# 工程間の整合性チェック（CPC）・手戻り連携 共通規約

> 本ファイルは「ある工程の生成物が、その工程の input となった直前工程の正本ドキュメントと整合しているか（用語・表記のゆれを含む）」という **固有の工程に限らず不変であるべきチェックロジック** を一元化する。各工程のレビュー機構（生成スキルの直後に置く「レビュー」に相当する位置）はこのファイルを参照し、内容を転記・重複させない。各工程固有の構造チェック項目（CPC-1）はローカルの観点表に個別定義する。

## 目的

- 8 工程（SA〜PT）のうち、UI・PG(backend) には前工程正本との整合性チェック機構が存在せず、SS・PG(frontend)・PT には存在するが「用語・表記の統一性」という観点が明文化されていないという、工程間で不均一な状態を解消する。
- 不整合発見時の対応手順（インラインフィックス判定・手戻りID採番・上位設計書確認・大規模手戻りエスカレーション）を単一の共通手順として正典化し、全レビュー機構が同一の手順を適用する。

## 工程別・生成物 vs 直前工程正本ドキュメント対応表

| 工程 | 生成スキル | 生成物 | 直前工程の正本ドキュメント | 整合性チェック機構 |
|---|---|---|---|---|
| SA | `requirement-doc-gen` | `docs/requirements/*` | issue原文（正式な設計資材ではない） | 対象外（前工程に正本ドキュメントが存在しない root 工程。本ファイルの対象工程から除外） |
| UI | `basic-design-gen` | `docs/base-design/*` | `docs/requirements/要件定義_{R###}.md`・`要件一覧.md` 等 | `/basic-design-review`（要件定義との整合性・CPC-2を含む） |
| SS | `detailed-design-gen` | `{スタック}/docs/detail-design/*`・WB | `docs/base-design/*` | `detailed-design-review-backend/batch/frontend` 観点B（基本設計との整合性・CPC-2を含む） |
| PG（backend） | `springer-scaffold` | `{スタック}/src/main` | `{スタック}/docs/detail-design/プログラム仕様書_{機能ID}.md`・WB | `springer-review` Step2.6（詳細設計整合性チェック・CPC-2を含む） |
| PG（frontend） | `reacter-code-gen` | `frontend/src/*` | `frontend/docs/detail-design/コンポーネント仕様書_{機能ID}.md`・WB | `reacter-code-review`（`reacter-review-crosscut` 観点a・CPC-2を含む） |

> SA 工程は「直前工程の正本ドキュメント」が存在しない（issue が唯一の入力であり、issue はワークフロー上の正式な設計資材ではない）ため、本ファイルの対象工程から除外する。

### 機械的ゲート（無条件生成の成果物パスの存在確認・SS/PG/PT）

上表の整合性チェック機構は、実行するかどうかが生成スキルの完了報告・作業者の遵守に委ねられており、レビュースキル自体が一度も実行されないままPRが作成・マージされる事象が実際に発生した。これを補うため、`.claude/hooks/check_review_gate.py`（PreToolUse・`gh pr create`/`pr-open.sh`をマッチ）が、SS/PG/PT 工程の機能ID別ブランチについて、レビュー実施時に**無条件で生成されるはずの成果物**の存在を確認し、無ければブロックする。

- 判定対象（存在確認のみ）:
  - SS: `{スタック}/specs/{案件キー}/detail-design/{issue_id}_{機能ID}/review-report.md`・同ディレクトリ配下の `adr/ADR-SS-{n}*.md`（最低1件）
  - PG: `{スタック}/specs/{案件キー}/implementation/{issue_id}_{機能ID}/springer-review-report.md`（backend系機能ID）または `reacter-code-review-report.md`（frontend系機能ID＝`front-`始まり）。ADR は不要
  - PT: `{スタック}/specs/{案件キー}/unit-test/{issue_id}_{機能ID}/consistency-report.md`。ADR は不要
- 判定対象外（本フックでは判断できない）: 外部IF定義書等、生成条件が可変な成果物／各成果物の内容の質（finding の解消状況等）

本ゲートは「レビューが実施された形跡があること」のみを保証する簡易ゲートであり、レビューの質そのものを保証するものではない（`check_backlog_gate.py`と同種の補助的な安全網）。

## CPC-1: 構造的一致

API 仕様・DB スキーマ・クラス一覧等、生成物の種類ごとに個別に定義される構造的な値の一致。生成物の種類ごとに確認内容が全く異なるため、**本ファイルでは汎用化・共通化しない**（共通化すると抽象的になりすぎて実効性を失うと判断したため）。各工程のレビュー機構が自身の観点表（例: `detailed-design-review-backend` の観点A・観点B、`springer-review` の観点台帳）にローカルで定義する。

## CPC-2: 用語・表記の統一性（本規約の主要スコープ）

生成物の記述に用いられている用語・項目名・エンティティ名・コード値・固有名詞等が、直前工程の正本ドキュメントにおける対応する記述と一致しているかを確認する。判定基準は No.54 の検討内容に基づき 2 段階とする。

| 区分 | 対象例 | 判定基準 |
|---|---|---|
| **定数的なもの** | 固有名詞・項目名・列名・エンティティ名・コード値・ID・メッセージコード等 | **完全一致**を要求する。表記ゆれ（別名化・言い換え・省略形の混在）は不整合として指摘する |
| **説明的な記述** | 処理概要・業務ルールの説明文等 | **意味的な一致**を要求する（表現の言い換え自体は許容するが、意味の齟齬・矛盾は不整合として指摘する） |

> 実例（No.54）: SS 工程が生成した `コンポーネント仕様書_F012.md` で「グルーピング」という語の指す対象が基本設計側の記述と不明確に食い違っていた（商品名という変更可能な値を不変の識別子のように扱う記述矛盾）。このように、値そのものの構造的一致（CPC-1）だけでは検出できない「語の意味・指示内容のズレ」を CPC-2 で捕捉する。

## 不整合発見時の手戻り連携手順（統一フロー）

不整合を発見した場合は **全て本手順を経由する**。「通常手戻り（閉じた修正）」と「rework（横断機構）」の2分岐は廃止し、単一フローで処理する。ルールを一本化することで人間・AI 双方の判断ブレを防ぐ（No.48「手戻りチケットを起票して対応させる」の徹底）。

### 手順1: インラインフィックス判定（チケット不要の例外）

以下を **すべて** 満たす場合のみ手戻りチケットなしで直接修正してよい:
- 設計変更を伴わない（WB・形式設計書・要件定義書等の変更なし）
- 工程で管理している資料（docs/）に影響しない
- 修正対象が 1 ファイル以下のコードレベル修正

インラインフィックスを行った場合は当該工程 issue のコメントに修正内容を 1 行記録する。

> **本判定は `docs-to-pr.md` Step 0（バックログ解消ゲート）からも遷移する。** バックログ解消の対応方針をユーザーに選択肢として提示する**前に**、AI は上記3条件を必ず自己チェックすること。3条件のいずれかが不成立（典型例: 解消のために別工程の正本ドキュメント`docs/`配下への変更を要する場合）と判定した時点で、「工程内で解消」を選択肢として提示せず、本ワークフロー（手順3以降）へ直接誘導する。この自己チェックを省略し、別工程正本への変更を伴う修正を即席の軽微PRとして処理してしまうと、手戻りID採番・issue起票を経ないままトレーサビリティを失った修正が発生する（過去に発生した実例を踏まえた対応）。

### 手順2: 既存チェックとの重複確認

設計書自体に誤りがある場合、同一レビュー機構内の複数の観点・チェックが同一の根本原因から個別に検出されうる。手戻りID採番の前に、今回の不整合が指す原因箇所（設計書の同一セクション）が、当該レビュー機構内の他の観点・チェックで既に別の不整合として記録されていないか確認する。同一原因の場合は手戻りIDを1つに統合し、レポート内で相互参照する（「関連: {他観点・他チェックの指摘番号}と同一原因」）。自動マッチングは行わず、人間・AIによる目視確認で十分とする。

### 手順3: 手戻りID 採番（インラインフィックス以外の全ケース）

```
1. specs/{案件キー}/meta.md の「手戻り管理表」に新規行を追記して手戻りID（sp-{3桁連番}）を採番
2. 影響工程と影響スタック・機能ID を特定
3. issue 運用の決定:
   実施工程（SS/PG/PT）かつ影響が閉じる → 既存 issue を Reopen
   計画・上流工程（SA/UI/SS-Plan/PG-Plan/PT-Plan） → 新規 issue 起票
   他スタック・他機能・他案件への波及  → 新規 issue 起票（実施工程でも）
4. ブランチ作成（-sp-{手戻りID} を付与）
5. rework-impact-report.md を作成する（格納先は原因工程に従う。SS/PG/PT〔スタックリポ側〕→ {スタック}/specs/{案件キー}/rework/{手戻りID}/／SA/UI/SS-Plan〔案件リポ側〕→ specs/{案件キー}/rework/{手戻りID}/）。push・PR対象。
```

### 本体PRマージ後に発覚した場合の手戻り判定（`docs-to-pr.md`「バックログ解消フォローアップPR」から接続）

対象issueの**本体（フェーズゲート）PRがマージ済み**の状態で、discussion-log・ADR間の同期漏れや記録の欠落が発覚した場合、以下の基準で手戻り相当かどうかを判定する。

- **判定基準**: `gh pr view {本体PR番号} --json mergedAt` で本体PRの `mergedAt` が非 null（マージ済み）であれば、そのissueの成果物は既に完了と判断された状態とみなし、**以後に発覚した欠落は規模の大小を問わず手戻り相当として扱う**（手戻りID採番・`rework-impact-report.md`作成を行う）。
- **issueのオープン/クローズ状態は判定に用いない。** issueクローズは「PRマージ後、レビュー確認済みの人間が行う」別の事務的ステップであり、これが実行されるタイミングに依存する不安定な指標のため、判定基準としない。
- **同一issue内の`specs/`（discussion-log・ADR）に閉じる修正は、新規issue起票を不要とする。** 手順3-3「issue 運用の決定」の「実施工程（SS/PG/PT）かつ影響が閉じる → 既存issueをReopen」の精神を踏襲し、対象issueが実際にはクローズされていない場合は「Reopen」操作の代わりに、手戻りの発生を明示するコメントを対象issueへ追加する運用とする。他工程・他スタック・他機能への波及がある場合は手順3・手順5の通常の判定に従う。

### 手順4: 設計変更時の上位設計書確認（必須）

```
WB・形式設計書・成果物を修正した場合:
  1. 基本設計（docs/base-design/）に影響するか → 影響あり: 修正して UI 工程の修正PR を促す
  2. 要件定義（docs/requirements/）に影響するか → 影響あり: 修正して SA 工程の修正PR を促す
```

### 手順5: 他スタック・他機能・他案件への波及（rework-trace + /rework-guide）

```
上位波及の判定（いずれか該当）:
  - 他スタックへの波及（共有テーブル・スタック間 I/F・認証設定の変更）
  - 他機能ID への波及（同一 API/テーブル/クラスを参照する別機能に影響）
  - 他案件（別 Milestone）への波及

エスカレーション手順:
  1. rework-trace エージェントを起動（縦診断）→ rework-impact-report.md
  2. /rework-guide を起動（横展開調査 → ADR-rework-{NNN} → -sp-{手戻りID} ブランチ誘導）
```
