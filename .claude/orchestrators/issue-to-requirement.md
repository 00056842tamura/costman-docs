# オーケストレーター定義: SA 工程（要件定義）フロー

## 目的
案件キー・SA issue を入力に、壁打ちしながら**要件定義成果物を `docs/requirements/` に直接作成**し、要件ID（R###）を採番する。

> 要件ID は業務要求単位の識別子（SA工程で採番）。スタック別・API/画面/ジョブ単位への分解と機能ID（`{カテゴリ}-{3桁連番}`）採番は UI 工程（`basic-design-gen`）が担う。

## 前提
- 案件開始（`/case-init`）・SA 着手（`/issue-init` 工程: SA）が完了し、以下が存在する:
  - `specs/{案件キー}/meta.md`（案件メタ）・`specs/{案件キー}/requirements/{issue_id}/`（検討メモ）
  - `feature/{案件キー}-sa`（作業ブランチ）・`docs/requirements/要件一覧.md`（R###採番台帳）
- **成果物は `docs/` へ直接書く**（直接編集モデル）。specs には検討メモ（discussion-log・adr）のみ残す。

## 入力
- 案件キー / SA issue-id / 対象チケット情報

## 実行手順

### Step 0: 本工程のDoDチェックリスト
壁打ちを始める前に、本要件で確定させる成果物とその項目を明示する（ゴールの提示。**この時点では質問しない**。質問はStep 3以降で1項目ずつ行う）。

1. **対象テンプレートの確定**: 下表（SA成果物カタログ）を参照し、当該要件の特性（画面の有無・帳票の有無・既存の業務概要/システム構成/業務フロー/コード値への影響有無）に応じて適用テンプレートを絞り込む。

   | テンプレート | 適用条件 |
   |---|---|
   | `要件定義_{要件ID}.md` | 全要件で必須 |
   | `要件一覧.md` | 全要件で必須（採番） |
   | `ユースケース図.md` | 全要件で必須 |
   | `画面遷移図.md` | 画面を伴う要件のみ必須 |
   | `業務概要.md` | 既存の業務概要に変更が生じる要件のみ更新 |
   | `システム全体図.md` | システム構成に変更が生じる要件のみ更新 |
   | `システム化業務フロー.md` | 業務フローに変更が生じる要件のみ更新 |
   | `コード定義書.md` | 新規コード値を伴う要件のみ更新 |
   | `画面レイアウト.md` | 画面を伴う要件のみ必須 |
   | `帳票レイアウト.md` | 帳票を伴う要件のみ必須 |

2. **チェックリストの生成**: 絞り込んだ各テンプレート（`docs/templates/30_要件定義/`配下）の見出し（`##`セクション。メタ情報系見出しを除く）を読み取り、見出しごとに「何を確定させるか」を1行で示す箇条書きを作る（固定リストではなく、テンプレートの現在の構成から都度生成する）。

3. **提示**: 生成したチェックリストをユーザーに提示する。

> 1つのissueに複数の要件ID（R###）が含まれる場合、DoDチェックリストは**要件ID単位**で個別に生成・管理する。
> プロダクト技術スタック（DB構成・フレームワークバージョン）の確定は Step 1.5 で別途行う（案件・プロダクト単位の一度限りの決定であり、要件ID単位の本チェックリストには含めない）。

### Step 1: 辞書・既存ドキュメント読み込み
`docs/glossary/` 全辞書を読み込む。存在すれば合わせて読む:
- `docs/requirements/業務概要.md` — 既存の業務範囲・関連システム・利用者区分
- `docs/requirements/要件一覧.md` — 既存要件（**要件ID の重複確認用**）
- `docs/requirements/コード定義書.md` — 既存コード値
- `docs/requirements/ユースケース図.md`・`画面遷移図.md` — 既存のアクター・ユースケース・画面遷移（重複確認）
- `docs/architecture/overview.md` — システム全体構成（**技術スタック表「データベース」「フレームワーク（バックエンド）」「フレームワーク（フロントエンド）」の各行を Step 1.5 で使用する**）

### Step 1.5: プロダクト技術スタック（DB構成・フレームワークバージョン）の確定（案件・プロダクト単位・初回のみ）
DB種別・DB方言、およびバックエンド（Springer/Spring Boot）・フロントエンド（React）のフレームワークバージョンは、要件ID単位で繰り返し確認するものではなく、**案件・プロダクト全体で1回だけ**確定する。確定後は `docs/architecture/overview.md`・各スタック `CLAUDE.md` に固定記述し、以降の UI/SS 工程は読み込み専用で参照する（ウォーターフォール＝再度決め直さない。台帳指摘「DBが決まるタイミングが遅い（工程4 SSの冒頭で決まっていた）」への対応）。

**A. DB構成**
1. Step 1 で読み込んだ `docs/architecture/overview.md` の技術スタック表「データベース」行を確認する。
2. **プレースホルダー（`RDB（プロダクト要件に応じて選定）`）ではなく具体的な DB 製品名が既に記載されている場合**: 本プロダクトでは確定済みと判断し、何もせず次へ進む（毎回聞き直さない）。判定に迷う場合（記述が具体的か曖昧か判断できない場合）はユーザーに確認する。
3. **プレースホルダーのままの場合**: 本 issue が当該プロダクトで初めて DB 選定に触れる SA issue である。ただし、対象要件が明らかに DB アクセスを伴わない性質だと判断できる場合は、AI の自己判断で「対象外（理由付き）」としてよい。判断の意図・理由を必ず1行以上明記し、Step 7 の discussion-log に記録する（理由の記載がない「対象外」は無効。次回以降の SA issue で改めて確認する）。
4. DB アクセスを伴う可能性がある場合は、ユーザーに DB 製品・方言を 1 回だけ確認する（可能であれば想定データ量・可用性要件等の選定根拠も記録する）。確定したら `docs/architecture/overview.md` の技術スタック表「データベース」行を確定値で直接更新する（例: `PostgreSQL 16`）。

**B. フレームワークバージョン（バックエンド Springer/Spring Boot・フロントエンド React）**
1. 影響する各スタックの `CLAUDE.md`（`bs/`・`us-api/`・`us-mpa/`・`batch/` の「フレームワーク・バージョン」節、`frontend/` の「UI フレームワーク」行）を確認する。
2. **「← TBD（確定時に更新）」等の未確定マーカーが無い場合**: 当該スタックは確定済みと判断し、何もせず次へ進む。
3. **未確定マーカーがある場合**: 本 issue が当該プロダクトで初めてフレームワークバージョンに触れる SA issue である。ユーザーにバックエンド（Springer 2＝Spring Boot 3 or Springer 3＝Spring Boot 4）・フロントエンド（React 19 or React 18）のバージョンを1回だけ確認する。
   - **デフォルト方針**: 特別な理由がなければ全バックエンドスタック共通で Spring Boot 4（Springer 3）を採用してよい。ただし `.claude/rules/product-rules.md`「1 プロダクト内で Springer 2 と 3 を混在させてよい」の規定は維持する（本Stepは全スタック一律の確定を強制しない。スタックごとに異なるバージョンが必要な場合はそのスタックの `CLAUDE.md` で個別に上書きしてよい）。
   - Reactバージョンに連動する依存ライブラリ（例: React Router — React 19→v7／React 18→v6）のバージョンも同時に確定し、`frontend/CLAUDE.md` の該当行を単一のバージョンに書き換える（`／v6`等の未確定な両論併記を残さない）。
4. 確定したら、対象スタックの `CLAUDE.md` から「← TBD（確定時に更新）」を除去して確定値のみを記載し、`docs/architecture/overview.md` の技術スタック表「フレームワーク（バックエンド）」「フレームワーク（フロントエンド）」行を確定値で更新する。
5. 対象外（DBアクセス同様、明らかに無関係と判断できる場合のみ）は AI の自己判断で「対象外（理由付き）」としてよい。理由の記載がない「対象外」は無効。

**A・B共通**
6. 本 issue で確定した項目（DB構成・フレームワークバージョンのいずれか、または両方）は、Step 8 の ADR 起票対象に含める（決定事項欄に確定した項目を明記し、影響スコープを「プロダクト全体（要件ID非依存）」とする）。
7. 本Stepの確認結果は、要件ID単位の Step 0 DoDチェックリストには含めない（プロダクト単位の決定であり、要件IDごとの繰り返し確認は行わない）。

### Step 2: issue の解釈
- issue タイトル・本文を読み込み、業務用語を辞書に従って解釈する。
- 辞書に未定義の用語をリストアップして確認する。

### Step 3: 不明点の洗い出し（Step 0のチェックリストを1項目ずつ消化する。一度に全部聞かない）
- Step 0で生成したチェックリストを先頭の項目から順に確認する。各項目について「確認済み」または「対象外（理由付き）」を記録する。
- 「対象外」と判定する場合は、AIの自己判断で確定してよい。ただし判断の意図・理由を必ず1行以上明記する（理由の記載がない「対象外」は無効）。
- 全項目の記録が完了するまで、次のStepへは進めない。

### Step 3.5: ユースケース・画面遷移の壁打ち
- **ユースケース**: 対象要件のアクター（利用者区分）とユースケースの関係を確認する（`ユースケース図.md` へ反映）。システム化業務フローと相互に補強する観点で、既存ユースケースとの重複・関連を確認する。
- **画面遷移**: 対象要件に画面がある場合、業務要求レベルの粗い画面遷移（遷移元・遷移先・契機）を確認する（`画面遷移図.md` へ反映。詳細な state 遷移は UI 工程の画面状態遷移図で扱う）。

### Step 4: 影響スタックの特定
- 直接変更が必要なスタックを列挙する（`frontend/` `bs/` `us-api/` `us-mpa/` `batch/`）。対象機能が複数のスタック構成で実現可能な場合（例: 新規画面が `frontend`+`us-api`〔SPA〕か `us-mpa`〔MPA〕か）は、トレードオフ（対話性・SEO/SSR要否・処理形態・既存の類似機能との一貫性）を対話で確認し、決定と理由を記録する（本工程は壁打ちが前提であり、確認自体を省略することはない）。管理機能か一般ユーザー向け機能かという対象ユーザー区分は、いずれの物理スタックを選ぶかとは独立した軸であり（UI工程で機能IDカテゴリ`us-intra`/`us-inter`として要件内容に基づき判定・確定する）、本Stepでのスタック選択の判断材料にはしない。
- US-API の I/F 変更がある場合は `frontend/` への影響も記録。
- `docs/architecture/stack-dependency.md` で循環依存が無いか確認する。加えて、決定した依存パターンが同ファイル「許可される依存関係」表に含まれるか照合する。含まれない新パターンの場合、「禁止される依存関係」表・循環依存に該当しないことを確認し、ユーザー承認（必要に応じ `.claude/rules/product-rules.md` に従い標準チーム相談）を得た上で、同ファイルの表を直接更新する（ドキュメントレベルの更新。物理的な `/stack-init` 実行は UI 工程完了後・SS-Plan ゲートで別途行う。このタイミングは変更しない）。
- 上記でスタック構成・依存関係表の更新を行った場合、Step 8 の ADR 起票対象に含める（決定事項欄に選定内容・更新した依存関係を明記）。
- 結果を `specs/{案件キー}/requirements/{issue_id}/meta.md`（工程issue meta）に記録する。

### Step 5: 要件ID（R###）の採番
- `docs/requirements/要件一覧.md` に対象要件を採番する（`R001`…・既存と重複しない 3 桁連番）。**ここが採番の正本**。
- `specs/{案件キー}/meta.md` の「要件ID 採番表」に同じ R### を追記する（工程横断トレース用の索引）。
- 1 つの issue に複数要件が含まれる場合は複数 R### を採番してよい。
- **機能ID（`{カテゴリ}-{3桁連番}`・スタック別・API/画面/ジョブ単位）はここでは採番しない**（UI 工程 `basic-design-gen` が要件IDを分解して採番する）。

### Step 6: per-要件 要件定義の作成（`docs/` へ直接）
- 要件ごとに `docs/requirements/要件定義_{要件ID}.md` を `docs/templates/30_要件定義/要件定義_{要件ID}.md` に従って**直接作成**する。
  - 目的・背景／対象ユーザー／要求一覧／受け入れ条件／非機能要件／制約／除外範囲を埋める。
- > PSK30 **一覧系**文書群（業務概要・システム全体図・システム化業務フロー・要件一覧詳細・コード定義書・画面レイアウト 等）は、Step 9 の **`/requirement-doc-gen`** がまとめて生成する（2 段階方式）。本ステップでは作らない。

### Step 7: 検討経緯の記録
`specs/{案件キー}/requirements/{issue_id}/discussion-log.md` に壁打ちサマリーと主要決定事項（ユースケース・画面遷移を含む）を記録する。

### Step 8: ADR 起票（強制ゲート）
> **ゲート条件**: Step 0のDoDチェックリストの全項目が「確認済み」または「対象外（理由付き）」として記録されていることを確認する。未解決の項目が残っている場合はStep 3に戻り解消する。Step 1.5でDB構成・フレームワークバージョンを確定した（または「対象外」と判定した）場合は、その記録もdiscussion-logに残っていることを確認する。

`discussion-log.md` に記録した壁打ちサマリーをもとに、**課題（決定事項）の内容ごとに ADR を起票する（1 ADR = 1 決定事項）**。Step 1.5 で DB 構成・フレームワークバージョンを確定した場合は、それぞれ1つのADRとして起票する（決定事項＝「DB構成（DB製品）の確定」または「フレームワークバージョン（Spring Boot／Reactバージョン）の確定」・影響スコープ＝プロダクト全体・要件ID非依存であることを明記する）。
`specs/{案件キー}/requirements/{issue_id}/adr/adr-template.md` を基に、壁打ちで合意した決定事項の数だけドラフトを作成する:
- 命名規則: `ADR-SA-{n}-requirements.md`（{n} は 001, 002, ... の連番。既にあるファイルの続きから採番する）
- 例: 決定事項が 2 つあれば `ADR-SA-001-requirements.md` と `ADR-SA-002-requirements.md` を作成する
- 各 ADR に記載する内容:
  - メタ情報（日付・ステータス・対象案件/issue・起票工程=SA）
  - 背景 ①状況（元チケットの概要・目的）／②課題・問題／③制約
  - 決定事項（この ADR が扱う 1 つの決定内容。影響スタック・スコープ・除外範囲・採番した R### など）
  - 理由（採用・却下した選択肢と根拠）／影響（後工程への影響）／未確定事項（チェックリスト）

全ドラフトをユーザーに提示し、承認後、各 ADR を `specs/{案件キー}/requirements/{issue_id}/adr/ADR-SA-{n}-requirements.md` として書き込む。

### Step 9: 要件定義書群の生成（`/requirement-doc-gen`）
2 段階方式の生成段。壁打ち・採番・per-要件要件定義・discussion-log・ADR が揃ったら、PSK30 一覧系文書群を生成する。
```
/requirement-doc-gen 案件キー: {案件キー} SA issue-id: {issue_id} 対象要件ID: {R###...}
```
- `docs/requirements/` に 業務概要・システム全体図・システム化業務フロー・要件一覧・コード定義書・画面レイアウト・ユースケース図・画面遷移図・〔帳票レイアウト〕を生成/差分追記する。
- 要件ID は `R001` 単一連番（正本＝`要件一覧.md`）。

### Step 10: 生成物の確認・修正（PR作成前）
`/requirement-doc-gen` の生成物を人間が確認し、誤り・不足に気づいた場合は PR 作成前に修正する。

1. 人間が生成物（`docs/requirements/*.md`・per-要件 `要件定義_{要件ID}.md`）を確認する
2. 問題なければ Step 11（PR作成）へ進む
3. 誤り・不足を発見した場合、指摘内容を Claude に伝える
4. 指摘を分類する:
   - 要件の内容・スコープに関わる誤り → `discussion-log.md` を更新し、`ADR-SA-{n}-requirements.md` を追加起票（既存 ADR は上書きしない）した上で該当ファイルを修正、または `/requirement-doc-gen` を再実行
   - 軽微な誤り（誤字・表記等） → 該当ファイルを直接修正（ADR 起票は不要）
5. 修正後、再度 1 に戻って確認する

### Step 11: SA 工程ゲート PR
`.claude/orchestrators/docs-to-pr.md` の手順に従い、SA 工程の PR を作成する
（工程=SA・ブランチ `feature/{案件キー}-sa`・ベース `feature/{案件キー}`）。生成済みの `docs/requirements/` 一式がレビュー対象。

### Step 12: PR レビュー指摘の取込み（承認まで繰り返す）
PR に変更要求・コメントが付いた場合、承認・マージに至るまで本ステップを繰り返す。

> 本ステップは PR が未マージの間のレビュー往復であり、手戻り（rework）とは異なる。
> 手戻りは PR マージ後に問題が発覚した場合にのみ適用する（`.claude/rules/product-rules.md` の手戻り統一ワークフロー）。
> 本ステップでは新規ブランチ・新規 issue は作らない。

1. 人間がレビュー指摘の取込みを指示する（例:「PR #{N} のレビュー指摘を取り込んで」。指摘本文の貼り付けでも可）
2. `gh pr view {N} --comments`（または本文貼り付け）でレビューコメントを取得する
3. 指摘を分類する:
   - 要件の内容・スコープに関わる指摘 → `ADR-SA-{n}-requirements.md` を追加起票する（{n} は既存 ADR の続きから連番。既存 ADR は上書きしない・決定の変遷を残す）
   - 軽微な修正（誤字・表現・記載漏れ等） → 該当ファイルを直接修正する（ADR 起票は不要）
4. `discussion-log.md` に指摘内容と対応方針を追記する
5. 該当ファイル（`docs/requirements/要件定義_{要件ID}.md` / `docs/requirements/*.md`）を修正する
6. 同一ブランチ（`feature/{案件キー}-sa`）に修正をコミット・プッシュする（新しい PR は作らない。既存 PR に追加コミットとして反映される）
7. 人間が再レビューを依頼する
8. 承認されるまで 1〜7 を繰り返す

### Step 13: 次工程（UI）への誘導
PR 承認・マージ後に進む。
```
✅ SA（要件定義）工程が完了しました。採番した要件ID: {R###...}
🎯 次のアクション — 基本設計（UI）工程:
   /issue-init 工程: UI 案件キー: {案件キー} ... で着手し、
   .claude/orchestrators/issue-to-design.md の手順に従って進めてください。
   （UI 工程で要件ID を スタック×API/画面/ジョブ単位の機能ID に分解します）
```

## 制約
- 技術的な実現方法はこのフェーズでは考えない（WHAT を固める）。**例外: DB構成（DB種別・DB方言）・フレームワークバージョン（Spring Boot／React）はプロダクト全体に影響する基盤決定のため Step 1.5 で確定する**（個別要件の実装方法・クラス設計等の技術的実現方法は対象外のまま）
- 勝手に決めず、必ず確認してから進める
- **成果物は `docs/` へ直接**（specs に成果物を置かない＝直接編集モデル）
- **`specs/`（discussion-log・adr）も `docs/requirements/` と同じ PR に含めて push する**（マルチリポ）
