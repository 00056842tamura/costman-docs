# オーケストレーター定義: UI 工程（基本設計）フロー

## 目的
案件キー・UI issue を入力に、壁打ちしながら**基本設計成果物を `docs/base-design/` に直接作成**する。
API 仕様・DB スキーマ・認証認可要件・実装対象クラス・ドメインモデルを確定させ、**要件ID（R###）をスタック×API/画面/ジョブ単位の機能ID（`{カテゴリ}-{3桁連番}`。カテゴリ: bs/batch/us-intra/us-inter/front-intra/front-inter）に分解して採番**する。

## 前提
- SA（要件定義）が完了し `docs/requirements/要件定義_{要件ID}.md` 等が存在する。
- UI 着手（`/issue-init 工程: UI`）が完了し、`specs/{案件キー}/base-design/{issue_id}/`・`feature/{案件キー}-ui`・`docs/base-design/機能一覧.md`・`docs/base-design/Web_API_IF一覧表.md` が存在する。
- **成果物は `docs/base-design/` へ直接書く**（直接編集モデル）。specs には検討メモ（discussion-log・adr）のみ残す。**実装対象クラス一覧・テストシナリオ・テーブル定義書・ロバストネス図・クラス図・画面状態遷移図も正式成果物として `docs/base-design/` へ直接生成する**（specsへの退避・検討メモ化はしない）。

## 入力
- 案件キー / UI issue-id / 対象要件ID（複数可）

## 実行手順

### Step 0: 本工程のDoDチェックリスト
壁打ちを始める前に、本機能で確定させる成果物とその項目を明示する（ゴールの提示。**この時点では質問しない**。質問はStep 2以降で行う）。

1. **影響スタック・機能特性の確認**: 対象機能が画面を持つか・DBスキーマ変更を伴うか・ファイルアップロード/ダウンロードを伴うか等を、Step 1で読み込む内容とSAの影響スタック特定結果を踏まえて確認する。

2. **対象テンプレートの絞り込み**: 下表（UI成果物カタログ）を参照し、当該機能の特性に応じて適用テンプレートを絞り込む。

   | テンプレート | 適用条件 |
   |---|---|
   | `機能概要.md` | 全機能で必須 |
   | `Web_API_IF定義書.md` | API/画面を持つ機能（bs/us-api/us-mpa/frontend）で必須 |
   | `シーケンス図.md` | 全機能で必須 |
   | `テーブル一覧.md`・`テーブル定義書.md` | DBスキーマ変更を伴う機能（bs/batch）のみ必須（テーブル単位。要件ID・機能ID単位ではない） |
   | `実装対象クラス一覧.md` | 全機能で必須 |
   | `テストシナリオ.md` | 全機能で必須 |
   | `クラス図.md` | 新規/変更Entityを伴う機能のみ必須 |
   | `画面状態遷移図.md` | frontend機能のみ必須 |
   | `機能一覧.md` | 全機能で必須（採番） |
   | `Web_API_IF一覧表.md` | API/画面を持つ機能のみ必須 |
   | `ファイルレイアウト一覧.md` | ファイルアップロード/ダウンロードを伴う機能のみ必須 |
   | `非機能共通設計.md` | 影響スタックにバックエンド系（bs/us-api/us-mpa/batch）または frontend が含まれる機能で必須（初回登場スタック区分はフル壁打ち、既存スタック区分は差分確認のみ。Step 1.6 参照） |

3. **チェックリストの生成**: 絞り込んだ各テンプレート（`docs/templates/40_基本設計/`配下）の見出し（`##`セクション。メタ情報系見出しを除く）を読み取り、見出しごとに「何を確定させるか」を1行で示す箇条書きを作る（固定リストではなく、テンプレートの現在の構成から都度生成する）。

4. **提示**: 生成したチェックリストをユーザーに提示する。

> 1つのissueに複数の機能ID（`{カテゴリ}-{3桁連番}`）が含まれる場合、DoDチェックリストは**機能ID単位**で個別に生成・管理する。

### Step 1: 前提ドキュメント読み込み
- `docs/requirements/要件定義_{要件ID}.md` — 要求一覧・受け入れ条件・非機能要件
- `docs/requirements/要件一覧.md`・`業務概要.md`・`ユースケース図.md`・`画面遷移図.md` — 既存要件・業務範囲
- `docs/base-design/機能一覧.md`・`テーブル一覧.md`・`クラス図.md` — 既存の機能ID採番・既存テーブルID採番・既存ドメインモデル（重複確認）
- `specs/{案件キー}/requirements/{SA issue_id}/discussion-log.md` — SA の壁打ち経緯
- `specs/{案件キー}/base-design/{issue_id}/meta.md` — 影響スタック（工程issue meta）
- `docs/glossary/` 全辞書・`docs/architecture/stack-dependency.md`・影響スタックの `CLAUDE.md`
- `docs/architecture/overview.md` — **SA工程で確定済みのDB構成（技術スタック表「データベース」行）。読み込み専用（Step 3 で使用。本工程では再度DB種別を選定しない）**

### Step 1.5: アーキテクチャ確認ゲート（SA決定の再確認）
Step1で読み込んだSAの影響スタック決定（`discussion-log.md`・関連する`ADR-SA-{n}`）を、これから設計するAPI/DB/画面の詳細レベルで再確認する。基本設計（UI工程）はアーキテクチャ詳細化の責務を持つため、SAの広い決定とUIでの詳細検討の間に認識相違がないかをここで払拭する。

- **相違なし**: discussion-logに確認済みである旨を1行記録し、Step2へ進む（Step2・Step6.5の機能IDカテゴリ判定の入力を確定させる位置づけであり、判定ロジック自体を変更するものではない）。
- **軽微な訂正**（本要件内で閉じる・SAの決定を単純に訂正するのみ）: `discussion-log.md`を更新し、該当する`ADR-SA-{n}`の「未確定事項」欄を更新する（Step9で既存の更新手順を使う）。新規`ADR-UI-{n}`として起票してもよい。
- **新規依存パターンが必要と判明した場合**（例: このAPIは想定外の別BSも呼ぶ必要がある等）: `issue-to-requirement.md`Step4と同じ手順（禁止依存・循環依存確認→ユーザー承認→`docs/architecture/stack-dependency.md`「許可される依存関係」表を直接更新）を踏み、`ADR-UI-{n}`として起票する。

> 本ステップは通常は数秒で完了する軽量な確認である。相違が見つかった場合のみ上記の訂正手順に進む。

### Step 1.6: 非機能共通設計の壁打ち（アプリ全体方針・初回登場スタック区分のみフル実施）
Step2以降で確認する「API/画面単位の認証・認可」等の前提となる、**プロダクト全体で1回だけ決める非機能・横断的な設計事項**を確認する。バックエンド系（bs/us-api/us-mpa/batch）とfrontendで確認項目が異なるため、今回issueの影響スタックに応じて該当するチェックリストのみ実施する。

**判定方法（`docs/base-design/非機能共通設計.md`の存在・記載内容ベース）:**
1. `docs/base-design/非機能共通設計.md` が存在しない → 本プロダクトで初めてのUI issue。今回issueの影響スタックに応じて該当するチェックリスト（下記）をフルに壁打ちする。
2. 存在する場合、今回issueの影響スタック区分（バックエンド系／frontend）ごとに、ファイル内の対応する見出し（`## バックエンド非機能事項` または `## フロントエンド非機能事項`）の記入状態を確認する:
   - 該当見出しがまだ生成されていない → そのスタック区分は本プロダクトで初登場のため、フルに壁打ちする。
   - 記入済み → 「今回のUI issueで新たに非機能決定が必要な事項はあるか」を一言確認するのみ（クラス図.mdの差分追記と同じ扱い。通常は数秒で完了）。「なし」の場合はdiscussion-logに「変更なし」と記録し次Stepへ進む。

**バックエンド非機能事項チェックリスト**（影響スタックにbs/us-api/us-mpa/batchのいずれかを含む場合）:
- 認証方式の全体方針／SecurityConfigの全体方針／パスワードハッシュ方式／セッション管理方針／CSP（バックエンド）／例外ハンドリング共通方針／ロギング共通方針

**フロントエンド非機能事項チェックリスト**（影響スタックにfrontendを含む場合）:
- アプリ名称／ブラウザタイトル／favicon／ログイン方式／共通レイアウト／ルーティング全体構成／エラーハンドリング共通方針／状態管理方針／環境変数の命名・管理方針／CSP（フロントエンド）

> 本Stepで確定した内容は Step 8 で discussion-log.md の `## 非機能共通設計の壁打ち` セクションに記録し、Step 9 で既存の `ADR-UI-{n}-design.md` 命名のまま起票する（専用のADR種別は設けない）。
> Step 2 の「認証・認可（必ず確認）」は本Stepで確定したアプリ全体方針を前提に、API固有のロール要件・アクセス可否のみを確認する（全体方針を重複して再確認しない）。

### Step 2: API 設計の壁打ち（1つずつ確認）
**エンドポイント:** HTTP メソッド/パス（フロント向け・内部 API を分けて）・レスポンスステータス（正常/異常）・ページネーション等
**認証・認可（必ず確認）:** 認証要否・アクセス可能ロール・SecurityFilterChain 変更要否・401/403 の使い分け
**リクエスト・レスポンス:** フィールドとバリデーション・機密情報の除外・空リスト/0件の扱い

**機能IDカテゴリの判定（バックエンド）:**
`bs`・`batch` は物理スタックへの機械的マッピングで確定する（対象読者という概念を持たないため追加の判定質問は発生しない）。

| 物理スタック | カテゴリ |
|---|---|
| `bs` | `bs` |
| `batch` | `batch` |

US層（`us-api`/`us-mpa`）は物理スタックの選択と `us-intra`/`us-inter` の判定を独立した軸として扱う。物理スタックは実装パターン（SPA向けJSON API か MPAサーバーサイドSSR か）の選択に過ぎず、対象APIが一般ユーザー向け（`us-inter`）か管理者相当（`us-intra`）かは、Step 6.5 の frontend 判定と同一の方法（`要件定義_{要件ID}.md`「対象ユーザー」欄・`業務概要.md`「利用者・権限」表の記述）に基づき、機能ID（API）単位で確定する。1つのAPIに一般ユーザー・管理者の双方が関与する場合は主たる利用者区分で判定し、判断が難しい場合はユーザーに確認する。

> Step 0チェックリストの `Web_API_IF定義書.md`（該当する場合 `Web_API_IF一覧表.md`）該当項目をここで消化する。

### Step 3: DB スキーマ設計の壁打ち
新規/既存カラム追加・主キー型と採番・一意/外部キー制約・楽観排他・インデックス・Flyway 命名（`V{日付}_{連番}__{説明}.sql`）。
**この壁打ち結果が `テーブル一覧.md`（テーブルID採番）＋`テーブル定義書_{テーブルID}_{テーブル名（論理）}.md`（bs/batch のみ）として確定する**（後続工程 SS では読み込み専用。実装時の変更は手戻りとして本工程に戻す）。
テーブルは複数の機能ID・要件IDから参照される場合があるため、テーブル単位（テーブルID）で識別する。要件ID・機能IDをテーブルの識別子・ファイル名には用いない。

> **DB種別・DB方言（PostgreSQL/Oracle等）は SA 工程で確定済み**（`docs/architecture/overview.md`）。本Stepでは読み込み専用で参照し、再度DB製品を選定しない。カラム定義のデータタイプ表記は SA 確定済みの DB 方言に従う。DB方言が「未選定」であることを本工程・後続の SS 工程の未確定事項として残さない（本工程時点で SA が未確定のまま UI に到達した場合は、手戻りではなく Step 8 の ADR で「SA 未確定のため UI 工程で暫定選定した」旨を明記し、`docs/architecture/overview.md` も合わせて更新する）。

> Step 0チェックリストの `テーブル一覧.md`・`テーブル定義書.md`（bs/batchのみ）該当項目をここで消化する。

### Step 4: ロバストネス図の壁打ち（ICONIX手法）
Step 2〜3 で確定した内容を Boundary（画面）・Control（業務ロジック・API受付を含む）・Entity（永続化される実体）に整理する。
- 各ユースケース（要件ID）につき、境界オブジェクト・制御オブジェクト・実体オブジェクトを洗い出す（**分析の単位はユースケース＝要件ID**。1要件IDが複数機能IDに分解される場合も、機能IDごとに分析を繰り返さない）
- 同一の業務アクションをControl（API受付）とControl（業務ロジック）の2ノードに二重表現しない。1つのAPIの責務が実装クラス単位内で明確に分離できる場合は、Controlノードを複数に分割してよい（判断基準は実装対象クラス一覧との対応）
- Entity は `docs/base-design/クラス図.md`（既存のドメインモデル）と対応させ、新規 Entity か既存 Entity かを確認する

> Step 0チェックリストの `ロバストネス図.md`（該当する場合 `クラス図.md`）該当項目をここで消化する。

### Step 5: 実装対象クラスの特定
ロバストネス図の Boundary/Control/Entity を具体的な実装クラスへ写像し、影響スタックと要求から作成・変更クラスを漏れなく列挙（Controller/Service I/F・Impl/Repository I/F・Impl/Mapper/Model/Request/View/Flyway/SecurityConfig/Enum 変更）。

> Step 0チェックリストの `実装対象クラス一覧.md` 該当項目をここで消化する。

### Step 6: フロント・バック間の責務分担
バリデーション分担（フロント Zod / バックエンド）・エラーメッセージの担当を確認。**破壊的操作（更新・削除等）に確認ダイアログを要するか**という業務レベルの方針もここで確認する（具体的なハンドラー名・処理シーケンスの詳細化はSS工程「アクション定義」の範囲であり本工程では行わない）。

### Step 6.5: 画面状態遷移の壁打ち（frontend 機能のみ）
画面（コンポーネント）が持つ state（Idle/Loading/Success/Error 等）と遷移契機（どの操作がどの状態遷移を起こすか）を確認する。`画面状態遷移図_{機能ID}.md` として確定する。
> ここで確定する遷移契機は、SS工程（`/detailed-design-gen`）の「アクション定義」（操作ごとのハンドラー関数名・処理シーケンス〔検証→API呼出→状態更新→画面遷移〕への詳細化）の出発点になる。本工程では契機と状態の対応までを確定し、ハンドラー実装レベルの詳細化はSS工程に委ねる。

**機能IDカテゴリの判定（frontend）:**
frontend は物理スタックが1つのみのため、Step 2 の US層判定と同一の方法で、対象画面が一般ユーザー向け（`front-inter`）か管理者（admin）相当（`front-intra`）かを、SA工程で収集済みの `要件定義_{要件ID}.md`「対象ユーザー」欄・`業務概要.md`「利用者・権限」表の記述を踏まえて、機能ID（画面）単位で確定する。1つの画面に一般ユーザー・管理者の双方が関与する場合は主たる利用者区分で判定し、判断が難しい場合はユーザーに確認する。

> Step 0チェックリストの `画面状態遷移図.md`（frontendのみ）該当項目をここで消化する。

### Step 7: 要件ID → 機能ID 分解方針の確認
Step 2〜6.5 で確定した内容を基に、対象要件ID（`R###`）を **スタック × API/画面/ジョブ単位** に分解する方針を確認する。
- 各スタックに何個の API/画面/ジョブが必要か（1要件が複数スタック・複数エンドポイントに跨る場合は全て列挙）
- 既存の API ID・ジョブID がある場合はそれを確認し、機能IDとの対応を明確にする
- 各分解単位のカテゴリ（`bs`/`batch`/`us-intra`/`us-inter`/`front-intra`/`front-inter`）は Step 2・Step 6.5 で判定済みの結果に従う
- US機能（`us-intra`/`us-inter`）が単一の `bs-XXX` への単純接続か、複数BS集約・独自業務ロジック・BS未呼出のいずれかの例外に該当するかを確認する（連番共通化の判断材料。確定した番号自体はStep 10で割り当てる）
- 分解結果は Step 10 の `/basic-design-gen` が機能一覧.md に採番する（本ステップでは方針の合意のみ）

> Step 8〜9 は壁打ち成果の確定（specs 検討メモ）。基本設計成果物そのものの生成・機能ID採番は Step 10 の
> `/basic-design-gen`（2 段階方式の生成段）が `docs/base-design/` へ直接行う。

### Step 8: discussion-log への記録
壁打ちのサマリーと主要設計決定事項（API/DB/認証認可/クラス構成/ロバストネス・ドメインモデル/画面状態/**非機能共通設計（アプリ全体方針）**/採用方式とその理由）を `specs/{案件キー}/base-design/{issue_id}/discussion-log.md` に**漏れなく**追記する。
> これが `/basic-design-gen` の主要入力になる。設計判断は本ログに残すこと。実装対象クラス一覧・テストシナリオ・テーブル定義書・ロバストネス図・クラス図・画面状態遷移図の内容も本ログに記録し、Step 10 でそのまま `docs/base-design/` へ生成する（specsへの中間ファイル退避はしない）。
> Step 1.6 の非機能共通設計の壁打ち結果は、専用見出し `## 非機能共通設計の壁打ち` を立てて記録する（`/basic-design-gen` が本セクションを機械的に読み取るため、見出し名を変更しないこと）。差分確認のみで「変更なし」だった場合もその旨を記録する。

### Step 9: ADR 起票（強制ゲート）
> **ゲート条件**: Step 0のDoDチェックリストの全項目（機能概要・シーケンス図・テストシナリオ等、専用Stepを持たない項目も含む）が「確認済み」または「対象外（理由付き）」として記録されていることを確認する。未解決の項目が残っている場合はStep 2〜6.5に戻り解消する。

`discussion-log.md` に記録した設計決定事項をもとに、**課題（決定事項）の内容ごとに ADR を起票する（1 ADR = 1 決定事項）**。
`specs/{案件キー}/base-design/{issue_id}/adr/adr-template.md` を基に、壁打ちで合意した決定事項の数だけドラフトを作成する:
- 命名規則: `ADR-UI-{n}-design.md`（{n} は 001, 002, ... の連番。既にあるファイルの続きから採番する）
- 例: 決定事項が 2 つあれば `ADR-UI-001-design.md` と `ADR-UI-002-design.md` を作成する
- 各 ADR に記載する内容:
  - メタ情報（日付・ステータス・対象案件/issue・起票工程=UI・関連 ADR `ADR-SA-{n}`）
  - 背景 ①状況（SA で確定したスコープ）／②課題（設計で解決が必要だった点）／③制約（API/DB/認証認可の制約）
  - 決定事項（この ADR が扱う 1 つの決定内容。API 設計・DB スキーマ・認証方式・実装クラス構成・ドメインモデル・**アプリ全体の非機能方針**〔認証方式全体・SecurityConfig方針・アプリ名称・ブラウザタイトル・ログイン方式・ルーティング全体構成等〕など）／理由／影響（後続工程への影響）／未確定事項

全ドラフトをユーザーに提示し、承認後、各 ADR を `specs/{案件キー}/base-design/{issue_id}/adr/ADR-UI-{n}-design.md` として書き込む。
その後、`specs/{案件キー}/requirements/{issue_id}/adr/ADR-SA-{n}-requirements.md` をすべて読み込み、UI で確定した内容については各 SA ADR の「未確定事項」欄を更新する。

### Step 10: 基本設計書群の生成（`/basic-design-gen`）
2 段階方式の生成段。壁打ち・discussion-log・ADR が揃ったら、要件IDを機能IDに分解・採番し基本設計成果物を生成する。
```
/basic-design-gen 案件キー: {案件キー} UI issue-id: {issue_id} 対象要件ID: {R###...}
```
- `docs/base-design/機能一覧.md` に要件IDをスタック×API/画面/ジョブ単位に分解した機能ID（`{カテゴリ}-{3桁連番}`）を、カテゴリごとに独立した連番で採番する。
- `docs/base-design/` に `機能概要_{機能ID}`・`Web_API_IF定義書_{機能ID}`・`シーケンス図_{機能ID}`・`テーブル一覧`（案件横断・累積・T###採番）＋`テーブル定義書_{テーブルID}_{テーブル名（論理）}`（bs/batch）・`ロバストネス図_{要件ID}`・`画面状態遷移図_{機能ID}`（frontend）・`実装対象クラス一覧`（UI issue単位・累積）・`テストシナリオ`（UI issue単位・累積）・`クラス図`（案件共通・累積）・`非機能共通設計`（案件横断・累積・Step1.6の壁打ち結果）・〔ファイル系〕を生成し、`Web_API_IF一覧表.md` に当該機能行を追記する。
- 外部IF定義書・メッセージ一覧・テスト計画書は本工程では作らない（後続工程の成果物）。

### Step 10.5: AIレビュー（`/basic-design-review`）
`/basic-design-gen` の生成物を、要件定義（`docs/requirements/`）との整合性・用語表記の統一性（CPC-2）観点でAIレビューする。
```
/basic-design-review 案件キー: {案件キー} UI issue-id: {issue_id} 対象要件ID: {R###...}
```
レビュー結果（`specs/{案件キー}/base-design/{issue_id}/review-report.md`）をStep11の人間確認に引き渡す。

### Step 11: 生成物の確認・修正（PR作成前）
`/basic-design-gen` の生成物と `/basic-design-review` のレビュー結果を人間が確認し、誤り・不足に気づいた場合は PR 作成前に修正する。

1. 人間が生成物（`docs/base-design/*.md`）と Step 10.5 のレビュー結果を確認する
2. 問題なければ Step 12（PR作成）へ進む
3. 誤り・不足を発見した場合、指摘内容を Claude に伝える
4. 指摘を分類する:
   - API設計・DBスキーマ・機能ID分解等の設計判断に関わる誤り → `discussion-log.md` を更新し、`ADR-UI-{n}-design.md` を追加起票（既存 ADR は上書きしない）した上で該当ファイルを修正、または `/basic-design-gen` を再実行
   - 軽微な誤り（誤字・表記等） → 該当ファイルを直接修正（ADR 起票は不要）
5. 修正後、再度 1 に戻って確認する

### Step 12: UI 工程ゲート PR
`.claude/orchestrators/docs-to-pr.md` の手順に従い、UI 工程の PR を作成する（工程=UI・ブランチ `feature/{案件キー}-ui`・ベース `feature/{案件キー}`）。生成済みの `docs/base-design/` 一式がレビュー対象。

### Step 13: PR レビュー指摘の取込み（承認まで繰り返す）
PR に変更要求・コメントが付いた場合、承認・マージに至るまで本ステップを繰り返す。

> 本ステップは PR が未マージの間のレビュー往復であり、手戻り（rework）とは異なる。
> 手戻りは PR マージ後に問題が発覚した場合にのみ適用する（`.claude/rules/product-rules.md` の手戻り統一ワークフロー）。
> 本ステップでは新規ブランチ・新規 issue は作らない。

1. 人間がレビュー指摘の取込みを指示する（例:「PR #{N} のレビュー指摘を取り込んで」。指摘本文の貼り付けでも可）
2. `gh pr view {N} --comments`（または本文貼り付け）でレビューコメントを取得する
3. 指摘を分類する:
   - API設計・DBスキーマ・機能ID分解等の設計判断に関わる指摘 → `ADR-UI-{n}-design.md` を追加起票する（{n} は既存 ADR の続きから連番。既存 ADR は上書きしない）
   - 軽微な修正（誤字・記載漏れ等） → 該当ファイルを直接修正する（ADR 起票は不要）
4. `discussion-log.md` に指摘内容と対応方針を追記する
5. 該当ファイル（`docs/base-design/*.md`）を修正する。修正が `テーブル定義書_{機能ID}.md` に及ぶ場合、SS工程は読込専用のため本ステップで確定させる
6. 同一ブランチ（`feature/{案件キー}-ui`）に修正をコミット・プッシュする（新しい PR は作らない）
7. 人間が再レビューを依頼する
8. 承認されるまで 1〜7 を繰り返す

### Step 14: 次工程（SS-Plan）への誘導
PR 承認・マージ後に進む。
```
✅ UI（基本設計）工程が完了しました。採番した機能ID: {bs-XXX / us-inter-XXX / front-inter-XXX ...}
   成果物: docs/base-design/{各種}_{機能ID}.md ・ 機能一覧.md / Web_API_IF一覧表 / 実装対象クラス一覧 / テストシナリオ / クラス図 / テーブル一覧 追記済み（DBスキーマ変更を伴う場合はテーブル定義書_{テーブルID}_{テーブル名}.md も生成）
   非機能共通設計.md: {初版生成 / 差分追記 / 変更なし}
🎯 次のアクション — 詳細設計計画（SS-Plan）工程: /issue-init 工程: SS-Plan 案件キー: {案件キー} → /issue-plan
```

## 制約
- 実装の詳細（具体的コード）は決めない（クラス名と責務の粒度まで）
- 勝手に決めず、必ず確認してから進める
- **成果物は `docs/base-design/` へ直接**（specs に成果物を置かない＝直接編集モデル）。実装対象クラス一覧・テストシナリオ・テーブル定義書・ロバストネス図・クラス図・画面状態遷移図も同様に `docs/base-design/` へ直接生成する（specsの中間ファイルには置かない）
- **`specs/`（discussion-log・adr）も `docs/base-design/` と同じ PR に含めて push する**（マルチリポ）
- Web_API_IF定義書・実装対象クラス一覧・テストシナリオ・クラス図は**プロダクトレベル**（複数スタックが参照）。テーブル一覧・テーブル定義書は bs/batch のみ・UI工程で確定し**SS工程は読み込み専用**（変更は手戻り）。外部IF定義書・メッセージ一覧・テスト計画書は SS/PT 工程の成果物（本工程では作らない）
- **テーブル定義書はテーブル単位（テーブルID=T###）で管理する（要件ID・機能ID単位ではない）**。1テーブルが複数の要件ID・機能IDから参照される場合があるため、機能ID分解（Step 7）とは独立にテーブルIDを採番する（Step 3）
