# 基本設計書群生成スキル（工程2 UI・2 段階方式の生成段）

`issue-to-design`（壁打ち）が確定させた API 設計・DB スキーマ・実装対象クラス・ロバストネス分析・検討経緯を入力に、
**要件ID（`R###`）をスタック×API/画面/ジョブ単位に分解し、カテゴリ別3桁連番の機能ID（`{カテゴリ}-{3桁連番}`）を採番**し、
PSK40 準拠の基本設計書群を **`docs/base-design/`（ルート集約）** に **直接生成**する（直接編集モデル）。

> 本スキルは新ワークフローの 2 段階方式の「生成段」。壁打ち・discussion-log・ADR は `issue-to-design`（オーケストレーター）が担う。本スキルは
> **機能ID採番＋UI 成果物の組み立て**に専念する。出力先は `docs/base-design/`（直接）。`specs/` には何も書かない。
> 実装対象クラス一覧・テストシナリオ・テーブル定義書・ロバストネス図・クラス図・画面状態遷移図も**正式成果物**として本スキルが生成する（specsへの検討メモ退避はしない）。
>
> **識別子体系**: 要件ID（`R###`・SA工程・業務要求単位）→ 機能ID（`{カテゴリ}-{3桁連番}`・UI工程・**1機能ID=1API/1画面/1ジョブ**・カテゴリは `bs`/`batch`/`us-intra`/`us-inter`/`front-intra`/`front-inter` の6種でそれぞれ独立した3桁連番）。
> 既存の API ID・ジョブID は維持し、機能ID とは対応表（`機能一覧.md`・`Web_API_IF一覧表.md`・`ジョブフロー一覧.md`）で管理する（識別子は一本化しない）。

## 入力形式
```
/basic-design-gen
案件キー: {案件キー}
UI issue-id: {issue_id}
対象要件ID: {R001 ...}
```

## 実行手順

### Step 1: 入力チェック
- [ ] `specs/{案件キー}/base-design/{issue_id}/discussion-log.md` が存在するか確認
- [ ] `docs/requirements/要件定義_{要件ID}.md`（対象要件分）が存在するか確認
- [ ] `specs/{案件キー}/base-design/{issue_id}/meta.md` を読み、影響スタック・対象要件IDを取得
- [ ] `docs/base-design/` が存在するか確認（なければ案件開始 `/case-init` が未実行）

### Step 2: 必要ドキュメントの読み込み
- `specs/{案件キー}/base-design/{issue_id}/discussion-log.md` — UI 壁打ちの設計決定（API/DB/認証/クラス/ロバストネス/画面状態/責務。**実装対象クラス一覧・テストシナリオ・テーブル定義書・ロバストネス図・クラス図・画面状態遷移図の生成元はすべて本ログ**）
- `docs/requirements/要件定義_{要件ID}.md` — 要求一覧・受け入れ条件・非機能要件
- `docs/requirements/要件一覧.md`・`画面レイアウト.md` — 要件ID 確認・画面項目
- `docs/base-design/機能一覧.md` — **既存の機能ID採番（対象カテゴリ内での重複確認・最大番号確認）**
- `docs/base-design/Web_API_IF一覧表.md` — 既存 API 一覧（重複確認）
- `docs/base-design/テーブル一覧.md`（存在する場合） — **既存テーブルID採番（重複確認・最大番号確認）**
- 変更対象テーブルの既存個票 `docs/base-design/テーブル定義書_{テーブルID}_{テーブル名（論理）}.md`（存在する場合） — 既存カラム定義（変更時の完全なカラム定義の土台）
- `docs/base-design/クラス図.md`（存在する場合） — 既存ドメインモデル（Entity 重複確認）
- `docs/base-design/非機能共通設計.md`（存在する場合） — 既存の非機能共通設計の記載内容（重複確認・差分追記〔初回登場スタック区分か既存区分か〕の判定に使用）
- 影響スタックの `CLAUDE.md` — ベースパッケージ・Springer バージョン

### Step 3: 機能ID（`{カテゴリ}-{3桁連番}`）の採番（要件ID → スタック×API/画面/ジョブ分解 → カテゴリ判定 → 連番割当）

対象要件ID（`R###`）ごとに、壁打ちで確定した影響スタック・実装対象クラスを基に、**スタック×API/画面/ジョブ単位**へ分解し、各分解単位のカテゴリを判定してからカテゴリ別の連番で機能ID（`{カテゴリ}-{3桁連番}`）を採番する。

#### 3-1. カテゴリ判定（`bs`/`batch`は物理スタックへの機械的対応、intra/interは要件内容に基づく判定）
`issue-to-design` の壁打ち（Step 2・Step 6.5）で確定済みの影響スタック・intra/inter判定結果から、以下の方法でカテゴリを決定する:

| 物理スタック | 種別 | カテゴリ | 判定方法 |
|---|---|---|---|
| `bs` | API | `bs` | 物理スタックへの機械的対応（新たな判定質問は追加しない） |
| `batch` | ジョブ | `batch` | 物理スタックへの機械的対応（新たな判定質問は追加しない） |
| `us-api` / `us-mpa`（discussion-log で「管理者向け」と確定したAPI） | API | `us-intra` | 要件内容（対象ユーザー）に基づく判定。物理スタック（us-api/us-mpa）の選択とは独立した軸 |
| `us-api` / `us-mpa`（discussion-log で「一般ユーザー向け」と確定したAPI） | API | `us-inter` | 同上 |
| `frontend`（discussion-log で「管理者向け」と確定した画面） | 画面 | `front-intra` | 要件内容（対象ユーザー）に基づく判定 |
| `frontend`（discussion-log で「一般ユーザー向け」と確定した画面） | 画面 | `front-inter` | 同上 |

#### 3-2. 連番の割り当て（カテゴリごとに独立した3桁連番）
- **`bs`・`batch`**: `docs/base-design/機能一覧.md` の当該カテゴリ内での最大番号+1（対象カテゴリ内に閉じた重複確認・最大番号確認。他カテゴリの番号とは独立）を割り当てる。
- **`us-intra`・`us-inter`**: 以下の優先順位で決定する:
  1. **原則（デフォルト）**: 当該US機能が単一の `bs-XXX` への単純な接続（1つの `bs-XXX` を呼び出すのみで、複数BS機能の集約・当該US機能固有の業務ロジックを持たない）である場合、その `bs-XXX` と**同じ連番**（`XXX`）を採用する（例: `bs-007` を単純中継する US 機能は `us-inter-007`）。
  2. **例外**（当該カテゴリ内の次の空き番号を採用し、機能一覧.md の「備考」列に理由〔`BS対応なし` または実際に依存する `bs-XXX`〕を明記する）:
     - (a) 複数のBS機能を集約する、または当該US機能固有の業務ロジックを持つ場合
     - (b) BSを一切呼び出さない場合（外部システム直接呼び出し・US層のみで完結する処理等）
     - (c) 対応する `bs-XXX` の番号が同一カテゴリ内で既に別の機能に使われている場合（衝突時のフォールバック）
- **`front-intra`・`front-inter`**: 当該カテゴリ内での最大番号+1を割り当てる（BS側との共通化はfrontendには適用しない）。

```
例: 要件ID R001（在庫を登録できる）が bs・us-api・frontend（一般ユーザー向け画面）に影響する場合
  bs-007          : bs       / API   / 在庫登録（bsカテゴリの次の空き番号）
  us-inter-007     : us-api   / API   / 在庫登録（bs-007への単純接続のため同一連番。C-9原則）
  front-inter-003  : frontend / 画面  / 在庫登録画面（front-interカテゴリの次の空き番号）
```

- `docs/base-design/機能一覧.md` に対象機能を採番する（既存の同カテゴリ内番号と重複しない3桁連番）。**ここが採番の正本**。
- 既存の API ID（`Web_API_IF一覧表.md`）・ジョブID（`ジョブフロー一覧.md`）がある場合は、機能一覧.md の「既存ID」列に記録して対応関係を管理する（識別子は一本化しない）。
- `specs/{案件キー}/meta.md` の「機能ID 採番表」に同じ機能ID・対応する要件ID を追記する（工程横断トレース用の索引）。
- 1 つの要件IDが複数スタック・複数API/画面/ジョブに分解される場合は複数の機能ID（カテゴリごと）を採番する（漏れなく列挙）。

### Step 4: 新規/修正判定（機能ID別）
`docs/base-design/シーケンス図_{機能ID}.md` の存在を確認する:
- **存在しない** → **新規機能**: 機能別ファイルを新規作成する
- **存在する** → **既存機能修正**: 機能別ファイルを今回の設計で上書き更新する

### Step 5: 各設計書の生成（PSK40 テンプレ構造を維持）
テンプレート参照先 = `docs/templates/40_基本設計/`。`_{機能ID}` 命名でコピー・記入する（**1機能ID=1API/1画面/1ジョブ**）。
**例外**: テーブル定義書は `_{テーブルID}_{テーブル名（論理）}` 命名とする（**1テーブル=1テーブルID**。機能IDは使わない）。テーブルは複数の機能ID・要件IDから参照されうるため、機能ID単位のファイル命名パターンをテーブル定義書には適用しない。

#### 機能一覧.md（追記・**カテゴリ別3桁連番・採番台帳の正本**）
- **今回採番済みの機能行のみ**を追記し、機能数合計を更新。既存行は変更しない。
- 採番規約は Step 3 を参照（種別別2桁・画面IDは使わない）。

#### 機能概要_{機能ID}.md
- 機能概要・入力・出力・処理概要・特記事項を、discussion-log と `要件定義_{要件ID}.md` から生成する。
- 1機能ID＝1API/1画面/1ジョブの粒度で記述する。

#### Web_API_IF定義書_{機能ID}.md（API を持つ機能のみ）
- 1機能ID＝1APIの構造で、メソッド/パス/リクエスト/認証認可/バリデーションを discussion-log から記述する。
- 200系等の正常応答のフィールド構造（業務データ）のみ discussion-log から記述する。
- **400/409等の標準エラー電文構造（`errorCode`/`message`/`detail[].Type`/`detail[].Field`/`detail[].ValidationMessage`）は discussion-log や推論で作成しない。`.claude/rules/springer-exception.md`「API エラーレスポンス構造（RestErrorInfo）」の定義を、フィールド名・大文字小文字（トップレベルは camelCase・`detail[]`内部は PascalCase）を含め一字一句転記する。** テンプレート（`docs/templates/40_基本設計/Web_API_IF定義書.md`）の400セクションは既にこの定義に準拠しているため、フィールド名を変更しない（サンプル値のメッセージ文言のみ当該APIのバリデーション内容に合わせて書き換えてよい）。

#### シーケンス図_{機能ID}.md
- discussion-log の API フローから Mermaid `sequenceDiagram` を生成。1機能ID＝1シーケンスの粒度で正常系・主要な異常系を記述する。

#### テーブル一覧.md・テーブル定義書_{テーブルID}_{テーブル名（論理）}.md（bs / batch のみ）
- discussion-log の DB スキーマ設計壁打ち結果から、新規テーブルにはテーブルID（`T001`…・既存と重複しない3桁連番。**正本は `docs/base-design/テーブル一覧.md`**）を採番する。テーブルは複数の機能ID・要件IDから参照されうるため、要件ID・機能ID単位では採番しない（1テーブル=1テーブルID）。
- **新規テーブル**: `テーブル一覧.md` に行（テーブルID・テーブル名・概要・参照する機能ID一覧）を追記し、`テーブル定義書_{テーブルID}_{テーブル名（論理）}.md` を新規作成する（カラム定義・インデックス・外部キー制約を記述）。
- **既存テーブルへのカラム変更**: 対応する既存の `テーブル定義書_{テーブルID}_{テーブル名（論理）}.md` を、変更後の全カラム定義で上書きする（テーブルIDは変わらない。他テーブルのファイルは変更しない）。`テーブル一覧.md` の概要・参照する機能ID一覧も必要に応じて更新する（既存の他テーブル行は変更しない）。
- 「参照する機能ID一覧」は参考情報として `テーブル一覧.md`・個票の両方に記録する（正本は `機能一覧.md`。テーブル定義書・テーブル一覧の正本はテーブルID・カラム定義側であり、機能ID列はあくまで参考）。

#### 実装対象クラス一覧.md（追記・UI issue単位で累積）
- discussion-log の実装対象クラス・フロント/バック責務分担から、スタック・レイヤー・クラス名・新規/変更・責務・対応機能IDを生成する。
- 既存の他 issue 分の記述は消さない（差分追記）。

#### テストシナリオ.md（追記・UI issue単位で累積）
- discussion-log と `要件定義_{要件ID}.md` の受け入れ条件から、受け入れ条件カバレッジ・UT観点・APIテスト観点・**コンポーネントテスト観点（frontendが対象スタックに含まれる場合。表示要素検証・Props/State変化検証・ユーザ操作検証・入力バリデーション）**・連結/E2Eシナリオを生成する。
- **「受け入れ条件カバレッジ」表を必ず埋める**（対象要件の受け入れ条件を全件カバー）。既存の他 issue 分の記述は消さない（差分追記）。

#### ロバストネス図_{要件ID}.md
- discussion-log のロバストネス分析（Boundary/Control/Entity）から Mermaid 図とオブジェクト一覧を生成する。1要件ID（＝ユースケース単位）＝1ロバストネス図。1要件IDが複数機能IDに分解される場合も分割せず、関連する全機能IDをメタ情報欄に列挙する。
- Mermaid 図（`flowchart LR`）は以下の構造ルールに従う:
  - 矢印は単方向のみとする（`Actor → Boundary → Control → Entity` の順。`Control → Boundary`・`Entity → Control` 等の戻り矢印は書かない）
  - 縦軸（列）は種別で揃える。ノード宣言・エッジ宣言は Boundary（画面）→ Control（API・業務ロジック）→ Entity の種別ごとにまとめて記述し、同種別のノードが同じ列に配置されるようにする
  - 1行1関係とする（1つの Boundary/Control ノードから複数の Entity・複数の Control へ分岐する場合も、行（エッジ群）を分けて記述し、1行に複数の Control・複数の Entity を並べない）
  - 他の行と接点を持たない独立したフロー（例: ログイン）はノード宣言・エッジ宣言の最後にまとめて配置し、他行のエッジ同士が交差しないようにする

#### クラス図.md（追記・案件共通で累積・Entity中心）
- discussion-log で新規に確定した Entity・関連のみを既存のドメインモデルクラス図に追記する。既存 Entity・関連は変更しない（重複させない）。

#### 画面状態遷移図_{機能ID}.md（frontend のみ）
- discussion-log の画面状態遷移壁打ち結果から Mermaid `stateDiagram-v2` を生成する。1機能ID（画面）＝1状態遷移図。

#### ファイルレイアウト一覧_{機能ID}.md・ファイル定義書_{機能ID}.md（ファイル入出力がある場合のみ）
- ファイルID（`F-IN-001` / `F-OUT-001`）を採番し、レイアウト定義・バリデーション・サンプルを discussion-log から生成する。

#### Web_API_IF一覧表.md（追記）
