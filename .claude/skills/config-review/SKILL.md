# プロジェクト構成レビュースキル

CLAUDE.md・README.md・settings.json・各スタック CLAUDE.md・docs/ の間の不整合を洗い出し、
検出した問題を**その場で修正**する。構成を更新するたびに実施することを想定している。

## 入力形式

> ⚠️ **実行前に `/clear` でコンテキストをクリアしてから起動すること。**
> 多数のファイルを順次読み込むため、既存の会話コンテキストが残っているとトークン上限に達する可能性がある。

```
/config-review
```

引数なしで実行する。プロダクトルートから起動すること。

---

## 実行手順

### Step 0: コンテキストクリアの確認

**会話が既に長くなっている場合は処理を中断し、以下をユーザーに伝える:**

```
⚠️ /config-review を実行するには先にコンテキストをクリアしてください。

  /clear

クリア後、改めて /config-review を実行してください。
```

会話がこのスキル起動直後（コンテキストが空に近い状態）であれば Step 1 に進む。

### Step 2: 9 観点の整合性チェック

#### チェック A: スキル実態 vs ドキュメント記載

1. `.claude/skills/` 配下のディレクトリ名を列挙し件数を数える
2. `CLAUDE.md` §6 に記載されたスキル名が `.claude/skills/` に実在するか確認する（スキル一覧の正本）
3. `README.md` §5.2〜5.10 各工程の「関連スキル」列に記載されたスキル名が `.claude/skills/` に実在するか確認する

**検出すべき問題例:**
- ファイルは存在するがドキュメントに未記載
- ドキュメントに記載があるがファイルが存在しない
- 件数表示（「N 種」）が実態と異なる

> ⚠️ 旧版 README.md が持っていた §3 ディレクトリツリーのスキル件数・§5.2 スキル確認リスト・§8.2 スキルテーブルは、章構成刷新（DEVELOPERガイド置換）で撤廃済み。現行版はスキル一覧を CLAUDE.md §6 と各工程の「関連スキル」列に分散して保持するため、参照先をこれらに変更した。

---

#### チェック B: フック設定の整合性

1. `settings.json` の `PreToolUse` / `PostToolUse` それぞれに記載されたスクリプト名を抽出する
2. `.claude/hooks/` に対応する `.py` ファイルが存在するか確認する
3. `CLAUDE.md` §7 のフックテーブルと照合する:
   - PreToolUse フックが全て「PreToolUse（書き込み前に実行）」セクションに記載されているか
   - PostToolUse フックが全て「PostToolUse（書き込み後に実行）」セクションに記載されているか
   - テーブルに余分な行・欠落した行がないか

**検出すべき問題例:**
- `settings.json` に記載があるがフックスクリプトが存在しない
- フックスクリプトが存在するが `settings.json` に未登録
- CLAUDE.md §7 のセクション（PreToolUse / PostToolUse）の分類が `settings.json` と異なる

---

#### チェック C: エージェント・オーケストレーター定義の整合性

**エージェント:**
1. `.claude/agents/` の実ファイル一覧を取得する
2. 各エージェントファイルが参照するスキル（`.claude/skills/{name}/SKILL.md`）が存在するか確認する

**オーケストレーター:**
1. `.claude/orchestrators/` の実ファイル一覧を取得する
2. `README.md` 内で参照されるオーケストレーターファイル名（`issue-to-requirement.md`・`issue-to-design.md`・`docs-to-pr` 等）が存在するか確認する

> ⚠️ 旧版 README.md §5.5・§8.3 のエージェント一覧、§3 ディレクトリツリーの orchestrators セクションは章構成刷新で撤廃済み。現行版はエージェント一覧を保持しないため、エージェント側は定義ファイル自身の自己整合性（参照スキルの実在）のみを確認する。

---

#### チェック D: バージョン整合性

以下のバージョン値をすべて読み取り、一覧表に整理する。

| 確認箇所 | 確認項目 |
|---|---|
| `docs/operation/environment_setup.md` §1 ツール表 | JDK・Node.js・Maven バージョン（**正本**。README.md §2 は Claude Code／Python／gh CLI のみを扱い JDK・Node.js・Maven は記載しないため対象外） |
| `docs/architecture/overview.md` 技術スタック表 | Java バージョン（SB3 / SB4） |
| `.claude/rules/springer-version-matrix.md` | Springer・Spring Boot・Java 対応表 |
| 全スタック `CLAUDE.md`（bs/ us-api/ 等） | Java バージョン宣言 |
| `_templates/*/CLAUDE.md` | Java バージョン記載 |
| `frontend/CLAUDE.md` | Node.js バージョン（`.nvmrc` との照合） |
| `frontend/.nvmrc` | Node.js バージョン |

読み取ったすべての値が一致しているか確認する。

---

#### チェック E: settings.local.json の健全性

1. `settings.local.json` が存在する場合、`permissions.allow` の全エントリを読む
2. 現在のワークスペースパス以外の絶対パスを含むエントリを検出する
3. 存在しないスクリプト名を直接参照するエントリを検出する
4. 汎用ワイルドカード（`python3 *` 等）以外の一時的なコマンドが残っていないか確認する

---

#### チェック F: 規約ルールファイルの参照整合性

1. `CLAUDE.md` §5「フレームワーク規約参照先」に記載された全ファイルパスについて `.claude/rules/` に存在するか確認する
2. 各スタック `CLAUDE.md` の「必須参照ルール」セクションに記載されたファイルが存在するか確認する
3. `.claude/agents/*.md` の「事前準備」で読み込むよう指示されたルールファイルが存在するか確認する

---

#### チェック G: docs/ と README.md の整合性

1. `docs/operation/environment_setup.md` から `README.md` への「セクション N」「§N」形式のクロスリファレンスを抽出し、参照先セクションが実在し話題が一致するか確認する（チェック I と合わせて実施）
2. `docs/architecture/overview.md` のスタック一覧（bs/・us-api/ 等）が実際のディレクトリと一致するか確認する
3. `README.md` §3.1 のリポジトリ別テーブルに記載された格納パス（`.claude/`・`_hint/`・`_templates/`・`docs/templates/`・`specs/{案件キー}/`・`{スタック}/docs/`・`{スタック}/specs/{案件キー}/` 等）が実在するか確認する
4. `README.md` §3.2 が参照する PNG（`docs/onboarding/*.png`）が実在するか、および `git status` で未追跡（untracked）になっていないか確認する

---

#### チェック H: ディレクトリ・ファイル記載の説明文整合性

**目的:** ドキュメント内のディレクトリツリーやファイル一覧において、各エントリの右側に説明文が記載されているか確認する。

**対象ファイル:**
- `CLAUDE.md`（§3 スタック配置ルール）
- 各スタック `CLAUDE.md`（ディレクトリ構成セクション）
- `_templates/*/CLAUDE.md`（ディレクトリ構成セクション）

> ⚠️ `README.md` は章構成刷新により §3 が「リポジトリ別テーブル＋PNG図解」形式に変わり `├──`/`└──` 形式のツリーを持たないため、本チェックの対象外とする（ツリーが復活した場合は対象に戻すこと）。

**確認手順:**

1. 上記ファイル内の **ツリー形式コードブロック**（`├──` / `└──` / `│` を含む）を全て抽出する
2. 各ツリー行のうち **ファイルエントリ**（ディレクトリではなくファイル名で終わる行）を対象とし、行末に説明文があるか確認する
3. ディレクトリエントリ（`/` で終わるもの）についても、その行自体に説明文があるか確認する（ただし `src/` `test/` `impl/` 等の慣用的な名称は除外してよい）
4. 説明文の有無の判定基準:
   - `# 説明` 形式（README.md スタイル）
   - `← 説明` 形式（スタック CLAUDE.md 内スタイル）
   - `... 説明` 形式（スタック CLAUDE.md ディレクトリ構成スタイル）
   - これらのいずれかが行内にあれば「説明文あり」と判定する

**検出すべき問題例:**
```
# 問題あり（説明なし）
├── issue-init/
├── MIGRATION_GUIDE.md

# 問題なし（説明あり）
├── issue-init/          # issue 作業ディレクトリ生成
├── MIGRATION_GUIDE.md   # 新規プロダクト取り込み手順
```

**除外対象（説明なしでも問題なし）:**
- `src/` `main/` `test/` `java/` `resources/` `impl/` `mapper/` など慣用的な Java/Maven ディレクトリ
- `├── ...` などのプレースホルダー行
- `│` のみの区切り行
- `<base-package>` などの可変プレースホルダーを含む行

---

#### チェック I: ドキュメント間クロスリファレンスの整合性

**目的:** `docs/` 配下の各ファイルが `README.md` を「セクション N」「§N」等の番号で参照している箇所について、参照先が実在し話題が一致しているかを確認する。README.md の章構成が変更されるたびに、この種のクロスリファレンスが古いセクション番号を指したまま残留するリスクがある（`docs/operation/environment_setup.md` で実際に発生した事例: §2 参照時に JDK/Node/Maven の記載が無い・§5.4 参照時にフックと無関係な内容だった）。

**確認手順:**
1. `docs/**/*.md`（`README.md` 自身を除く）から `README.md` の近傍に `セクション\s*\d+(\.\d+)?` または `§\d+(\.\d+)?` を含む文を grep で抽出する
2. 各参照について、`README.md` の目次・見出し（`## N.` / `### N.M`）に該当する番号の見出しが実在するか確認する
3. 見出しが実在する場合、参照元の文脈（前後の説明文）と見出しの話題が一致しているか目視で確認する（例: 「フックの動作確認は §5.4 を参照」に対し §5.4 の見出しが「工程2 UI 基本設計」であれば話題不一致）

**検出すべき問題例:**
- 参照先のセクション番号が存在しない（章構成の変更で番号がずれた）
- セクション番号は存在するが話題が一致しない（章の入れ替え・挿入で意味がずれた）

---

### Step 3: 問題の修正

検出した問題を以下の方針で**その場で修正**する。

| 問題の種類 | 対応 |
|---|---|
| ドキュメントの記載漏れ・カウント誤り | ドキュメントを修正する |
| バージョン不一致 | 全ファイルを最新バージョンに統一する（どのバージョンが正しいか不明な場合はユーザーに確認する） |
| ドキュメントの分類誤り（PreToolUse / PostToolUse 等） | ドキュメントを修正する |
| `settings.local.json` の stale エントリ | 対象エントリを削除する |
| ファイルが存在しない（ドキュメントに記載があるが実ファイルが無い） | **修正せず**ユーザーに報告する |
| ツリー内エントリに説明文がない | そのファイル・ディレクトリの用途を推定し、該当行の末尾に `# 説明` / `← 説明` / `... 説明` を追加する（既存行の説明スタイルに合わせること） |
| ドキュメント間クロスリファレンスの断裂（セクション番号の参照先が存在しない／話題が一致しない） | 原則として参照元ドキュメント（`README.md` 以外の側）を修正する。参照先の話題が本当に必要で `README.md` 側に章を新設すべきと判断される場合はユーザーに確認してから追加する |

> ⚠️ **ファイルの新規作成・削除は行わない。** ドキュメントの記述を実態に合わせる方向で修正する。
> バージョン変更など判断が必要な場合はユーザーに確認してから修正する。

## 制約

- ✅ 検出した問題は可能な限りその場で修正する
- ✅ バージョン変更など判断が伴う修正は変更前にユーザーに確認する
- 🚫 実装コード（`.java` / `.ts` / `.tsx`）は修正しない（対象はドキュメント・設定ファイルのみ）
- ✅ `README.md` の改訂履歴には今回の修正内容を追記する
  - 改訂履歴に記載する日付は、スキル実行日が**土曜・日曜の場合は直前の金曜日**の日付を使用する
- ✅ 修正後は変更したファイルの一覧を結果レポートに含める
