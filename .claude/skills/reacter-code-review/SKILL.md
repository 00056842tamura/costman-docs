# Reacter コードレビュー（観点台帳・固定クラスタ・2パス検証）

reacter フロントエンド（`frontend/`）のコードを、観点台帳に基づきクラスタ別サブエージェントでレビューする。**メインエージェントはオーケストレーターに徹し、修正は行わない。**

## 設計の要点

- **観点台帳**: `.claude/agents/reacter-review-checklist.md`（C1〜C6 の全観点を ID・制約レベル・分類・出典・適用条件で定義）を唯一の真実とする。
- **固定クラスタ分割**: レビューは観点台帳のクラスタ C1〜C6 に固定割当する（動的に観点を分けない）。各クラスタはちょうど1サブエージェントが担当 → カバレッジが決定論的。
- **プロンプト・スライス**: 各クラスタエージェントには台帳の**自クラスタ行だけ**を渡す（他クラスタ行は渡さない）。ノイズと取りこぼしを抑える。
- **未評価0件ゲート**: 各クラスタは担当の**規範行（C-行）すべて**に `準拠/違反/非該当` を付与する。
- **参考観点（任意 MAY）**: 台帳付録の参考観点（`REF-`、参考・推奨実装パターン由来）は**ゲート対象外**。規範行を全件判定したうえで明確な逸脱があれば MAY で**任意報告**してよい（報告は義務ではない）。
- **分類は台帳で確定**: MUST/SHOULD/MAY は台帳「分類」列をそのまま使う（✅/🚫→MUST、✨/⚠→SHOULD、条件付き(任意)/参考/非紐づけ→MAY、条件付きで条件成立時✅必須は MUST）。実装状況・動作可否・文脈判断を理由とした格下げは禁止。唯一の例外は台帳「適用条件」の条件成立可否。
- **2パス検証**: 1パス目の結果を `reacter-review-verifier` が敵対的に再検証する。

## レビュー観点と担当

| 観点 | 内容 | 担当 |
|---|---|---|
| a | 設計書整合（受け入れ条件・正常/異常/エッジ） | `reacter-review-crosscut` |
| b | プログラミングルール準拠 | クラスタ C1〜C6（台帳） |
| c | エラーハンドリング漏れ | ルール紐づき分は C1/C6 等、残余は `reacter-review-crosscut` |
| d | 重複・可読性・保守性 | `reacter-review-crosscut`（原則 MAY） |

## サブエージェント（`.claude/agents/`）

| クラスタ | エージェント | 担当 ID |
|---|---|---|
| C1 通信 | `reacter-review-comms` | COM-01〜08 |
| C2 セキュリティ・ビルド | `reacter-review-secbuild` | SEC-01〜24 |
| C3 スタイル | `reacter-review-style` | CSS-01〜04 |
| C4 フォーム | `reacter-review-form` | FRM-01〜13 |
| C5 構造・規約・性能・ルーティング | `reacter-review-structure` | STR-01〜36 |
| C6 状態・エラー・テスト・共通部品 | `reacter-review-quality` | QLT-01〜33 |
| 横断（a/d/c残余） | `reacter-review-crosscut` | （台帳外・網羅ゲート対象外） |
| 2パス検証 | `reacter-review-verifier` | 1パス目の再検証 |

## 入力形式

```
/reacter-code-review
frontend/src/features/item/
```

または

```
/reacter-code-review

Component: frontend/src/features/item/components/ItemForm.tsx
Hook:      frontend/src/features/item/hooks/useItem.ts
```

## 手順

1. **対象選別**: レビュー対象ファイル群を確定する（対象アプリは `frontend/` 単一スタック）。issue 作業中なら `frontend/specs/{案件キー}/detail-design/{issue_id}_{機能ID}/` の設計ドキュメントも特定する。
2. **（推奨）機械検出の前段**: `React.FC`/`any`/`dangerouslySetInnerHTML`/`innerHTML`/`console.log`/`debugger`/バージョンワイルドカード等を Grep で先に全ヒット特定し、確定違反の取りこぼしを防ぐ（`.claude/hooks/check_typescript.py` と同じ検出観点）。結果は該当クラスタエージェントへ渡す。
3. **1パス目（並列・最大5多重）**: クラスタ C1〜C6 の各サブエージェントと横断エージェントを起動する。各エージェントには次を渡す:
   - 対象ファイルパス
   - **台帳から該当クラスタ行だけをスライスしたテキスト**（プロンプト・スライス）
   - 「インデックス表を見るだけでなく担当観点に関連する出典ガイドを Read してからレビューすること」「未評価0件」「行番号を全件列挙」「曖昧表現禁止」「分類は台帳の値をそのまま使い格下げ禁止」の指示
4. **2パス検証（並列）**: クラスタ C1〜C6 と横断（crosscut）の計 7 件分の検証を **1 メッセージで並列起動** する。`.claude/agents/reacter-review-verifier.md` を読み込み、その内容をプロンプト冒頭に含めて Agent ツールを呼び出す。各検証に渡す情報: クラスタ名（または `crosscut`）、対象ファイルパス、**当該クラスタの1パス目判定結果**。検証エージェントの「追加違反 / 判定訂正 / 未評価」の指摘を、各クラスタの結果に反映する。
5. **統合・確定**: verifier の指摘を各クラスタの1パス目に反映し、最終判定を確定する。
6. **件数統一チェック**: ステップ5で確定した全クラスタの結果に対し、以下を確認してからステップ7へ進む。不一致があれば該当箇所を修正してから次のステップへ進む。
   - 全観点IDファイルの `指摘件数:` と `### N.` の連番が一致しているか
   - 複数ファイルの指摘が1つの `### N.` にまとまっていないか（ファイル単位で分割されているか）
   - 件数の単位（ファイル単位）がクラスタをまたいで統一されているか
7. **出力**: 下記「出力要件」に従い表示＋ファイル出力する。

## ⚠ 実行上の制約（必読）

- **Bash ツールで `cd` を使用しない**: CWD を変更するとフックの相対パスが壊れ Write/Edit ツールがブロックされる。ファイルパスは常に絶対パスで指定する。
- **レポートファイルの書き込みは Write ツールのみ使用**: Python スクリプト・`node -e`・`printf` 等のシェルコマンドによる代替書き込みは禁止。Write ツールがブロックされた場合は原因を調査し解消してから書き込む（フックエラーは `.claude/settings.json` の CWD 問題が原因）。

## 出力要件

メインエージェントは結果を表示するとともに、**複数ファイルに分けて**出力する。

### 出力先ディレクトリ（タイムスタンプ別）

**タイムスタンプの取得（必須・推定値を使わないこと）**

フォルダ名に使う `YYYYMMDD_HHMMSS` は、モデルが推定した値を**絶対に使わない**。
ファイル出力の直前に以下の PowerShell コマンドを実行し、その出力値をそのままフォルダ名に使用すること：

```powershell
Get-Date -Format "yyyyMMdd_HHmmss"
```

**issue 作業中（PG 工程・機能ID別ブランチ）の場合**: `frontend/specs/{案件キー}/implementation/{issue_id}_{機能ID}/reacter-code-review-report.md` に**単一ファイル**として出力する（下記「生成ファイル構成」の内容を1ファイルに集約する。工程間整合性ゲートが本ファイルの存在確認のみで機能できるよう、`springer-review` の `springer-review-report.md` と同じ命名パターンに揃える）。
issue が特定できない場合（アドホック実行）は `reports/reacter_code_review/reacter_code_review-{対象名}-{YYYYMMDD_HHMMSS}/` 配下に、下記「生成ファイル構成」のとおり複数ファイルに分けて出力する。
- 各ファイルは **Write ツール・絶対パス**で個別に書き込む（「⚠ 実行上の制約」を厳守。`cd` 禁止・シェルでの書き込み禁止）。

### 生成ファイル構成

```
reacter_code_review_YYYYMMDD_HHMMSS/
├─ summary.md          # サマリ（正確な件数・全指摘の要約一覧）
├─ MAY.md              # MAY 指摘を全件まとめる
├─ {観点ID}.md         # MUST / SHOULD 指摘を観点ID単位で1ファイル（例 SEC-01.md, STR-03.md）
└─ ...                 # 指摘のある観点ID（分類 MUST/SHOULD）の数だけ生成
```

- **観点IDファイル（`{観点ID}.md`）**: 分類が **MUST または SHOULD** の指摘を、台帳の観点ID単位で 1 ファイルにする。**指摘が 1 件以上ある観点IDのみ生成**（0 件の ID はファイルを作らない）。1 観点IDに複数の指摘箇所があれば**全件**を 1 ファイルに列挙する。
  - 観点IDの分類は台帳で確定済み（その ID は MUST か SHOULD のいずれか）。ファイル冒頭に分類を明記し、**MUST と SHOULD が一目で判別できる**ようにする。
- **`MAY.md`**: 分類 MAY の指摘（条件付き任意・参考 `REF-`・横断の可読性/保守性・ルール非紐づけ）を**全件**まとめる。観点IDごとには分けない。
- **`summary.md`**: 全指摘の要約一覧と**正確な件数**。曖昧件数は禁止。

### 記載ルール（全ファイル共通・重要）

**場所の記載ルール**
- 問題箇所が複数ある場合でも、**ファイル名と行番号をすべて個別に列挙**する。件数まとめ・「複数ファイル」等の概略表記は禁止。
- 1 箇所: `` `path/to/file.tsx` (L12) `` または `(L12-L20)`。複数箇所は箇条書きで各行を列挙。

**曖昧表現の禁止**
- すべてのフィールド（場所・問題点・修正案・タイトル・サマリ表・件数）で「等」「〜など」「多数」「複数箇所」「複数ファイル」「XX以上」「XX件以上」「概算」「〜他」を禁止する。
- 件数・ファイル数・観点ID数は**正確な数**を記載する（例: ×「20ファイル以上」→ ○「21ファイル」）。`summary.md` の件数は観点IDファイル・MAY.md の実件数と一致させる。
