# Springer レビュー修正リコンサイル（工程6 PG・プロダクト版）

`/springer-review` が出力したレビューレポートを入力に、**全 finding を漏れなく消し込む**ためのスキル。チャット上の指摘ではなく、**レポートファイルを唯一の真実**として扱い、ステータスで対応状況を追跡する。

修正 → レポートのステータス更新 → **未対応 0 件ゲート** → 差分再レビュー、を回す。

> レポートは specs（push・PR対象）。最新版（既存ワークフロー）の review-fix を新構造へ移植。

## 入力形式

```
/springer-review-fix
案件キー: inventory-2026-001
機能ID: bs-001
スタック: bs
PG issue-id: {issue_id}
```

引数にレビューレポートの `summary.md` パスを渡す。省略時は対象を確認する。

## 原則

- ✅ **必須 (ALWAYS)**: レポートの全 finding（MUST / SHOULD / MAY および「横断」）を対象にする。チャットの記憶や要約で済ませない。
- ✅ **必須 (ALWAYS)**: 各 finding のステータスを `未対応` → `対応済` または `対応不要（理由）` のいずれかに更新する。
- 🚫 **禁止 (NEVER)**: 分類 `MUST` の finding を理由なく未対応のまま残さない。
- ✅ **必須 (ALWAYS)**: 最終的に **`未対応 0 件`** を保証する（残る場合は未完了として報告し、理由を明示）。

## 実行手順

### Step 1: レポート読み込みと突合

1. 指定された `summary.md` を読み込み、全 finding（観点 ID / 分類 / 制約レベル / ファイル:行 / 内容 / 修正案 / ステータス）を全件把握する。詳細は各 `{観点ID}.md`・`MAY.md` を参照する。
2. 「横断（X-xx）」セクションの指摘も対象に含める。
3. ステータスが `未対応` の件数を数え、対応計画を提示する（分類 `MUST` → `SHOULD` → `MAY` の順）。

### Step 2: 修正の適用（分類順）

各 `未対応` finding について：

1. 対象ファイルの該当行を確認し、観点 ID に対応する規約（台帳 `.claude/agents/springer-review-checklist.md` の「出典」列のルールファイル、例: `.claude/rules/springer-controller.md`）に沿って修正する。
2. 修正できたら、レポートの当該行のステータスを **`対応済`** に更新し、備考に修正概要（例: `ResponseEntity 返却に変更`）を記す。
3. 現行仕様・ロジックを壊すため修正できない／対応不要と判断した場合は、ステータスを **`対応不要（理由）`** に更新する（理由必須）。
4. ⚠️ **注意 (CAUTION)**: 修正は既存フック（`check_java.py` 等）の検査も通す。修正で新たな規約違反を作らないこと。

### Step 3: 未対応 0 件ゲート

- レポートに `未対応` が残っていないことを確認する。
- 残っている場合は**未完了**として残件を一覧化し、理由とともに報告する（分類 `MUST` の未対応は原則許容しない）。

### Step 4: 差分再レビュー（デグレ・新規違反の検出）

1. 今回**修正したファイルのみ**を対象に `/springer-review` を再実行する（または該当レイヤーの reviewer エージェントを起動）。
2. 修正により**新たに発生した違反（デグレ）**がないか確認する。
3. 新規違反が見つかったらレポートの `summary.md` に追記（観点 ID・分類 `MUST`/`SHOULD`/`MAY`・ステータス `未対応`）し、Step 2 に戻って消し込む。
4. 新規違反が無くなるまで繰り返す（収束させる）。

### Step 5: 完了報告
```
✅ レビュー指摘を消し込みました（工程6 PG・{スタック}×{機能ID}）。
   対応済 N 件 / 非該当 M 件 / 未対応 0 件
📄 更新レポート: {スタック}/specs/{案件キー}/implementation/{issue_id}_{機能ID}/springer-review-report.md（push・PR対象）
🎯 次のアクション: docs-to-pr（PG・スタックリポ・コード＋実装docs を PR）

## 制約
- 🚫 レポートに無い finding を勝手に作らない／レポートの finding を勝手に消さない（ステータス更新で管理）
- ✅ レポートを唯一の真実とし、**未対応 0 件**を達成してから完了する
- ✅ 修正は `{スタック}/src/main/`（コード）。レポートは specs（push・PR対象）
- ✅ 差分再レビューで新規 finding が出たら追記して再消し込み
