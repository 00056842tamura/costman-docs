# AI整合性チェックスキル（工程8 PT 内）

`スタック×機能ID` の詳細設計・製造コード・テストコードの三者が整合しているか確認する（S3＝PT工程内で確定）。

> `phase-{N}` 概念は廃止。

## 入力形式

```
/consistency-check
案件キー: inventory-2026-001
機能ID: bs-001
スタック: bs
PT issue-id: {issue_id}
```

---

## 実行手順

### Step 1: 対象ファイルの収集

対象スタックが Springer系（`bs`/`us-mpa`/`us-api`/`batch`）か `frontend`（Reacter）かでパスが異なる。

**Springer系の場合:**

**詳細設計（基準・新構造）:**
- WB: `{スタック}/specs/{案件キー}/detail-design/{issue_id(SS)}_{機能ID}/{controller,service,repository}.md`
- 形式設計書: `docs/base-design/テーブル定義書_{テーブルID}_{テーブル名（論理）}.md`（UI工程が正本・テーブル単位）・`{スタック}/docs/detail-design/外部IF定義書.md`

**テストシナリオ（基準）:**
- `docs/base-design/テストシナリオ.md`

**製造コード（実態）:**
- `{スタック}/src/main/java/{パッケージパス}/controller/*.java`・`service/impl/*.java`・`repository/impl/*.java`・`repository/mapper/*.xml`

**テストコード（実態）:**
- `{スタック}/src/test/java/{パッケージパス}/controller/*Test.java`・`service/impl/*Test.java`・`repository/impl/*Test.java`

**`frontend`（Reacter）の場合:**

**詳細設計（基準）:**
- WB: `frontend/specs/{案件キー}/detail-design/{issue_id(SS)}_{機能ID}/frontend.md`
- 形式設計書: `frontend/docs/detail-design/コンポーネント仕様書_{機能ID}.md`

**テストシナリオ（基準）:**
- `docs/base-design/テストシナリオ.md`（「コンポーネントテスト観点」セクション）

**製造コード（実態）:**
- `frontend/src/features/{機能}/**/*.tsx`・`*.ts`

**テストコード（実態）:**
- `frontend/src/test/features/{機能}/**/*.test.tsx`・`*.test.ts`（[STR-36] のミラーリング配置。Springerの `src/test/java` と同一パターン）

### Step 2: 三者整合性チェック（4チェック）

#### チェック A: 詳細設計書 → 製造コードの整合性

| 確認項目 | 確認方法 |
|---|---|
| APIパス・HTTPメソッドがコードと一致するか | controller.mdのメソッド定義と `@GetMapping` 等を照合 |
| メソッドシグネチャ（引数・戻り値型）が一致するか | 各mdファイルのシグネチャとコードを照合 |
| バリデーションアノテーションが単体項目チェック仕様と一致するか | controller.mdのチェック仕様とRequestクラスを照合 |
| 業務ルールがServiceに実装されているか | service.mdの業務ルール欄とServiceImplコードを照合 |
| SQLがMapper XMLの内容と一致するか | repository.mdのMapper XML欄と実際のXMLを照合 |
| トランザクション設定が設計書と一致するか | service.mdのトランザクション欄と `@Transactional` を照合 |
| （`frontend`の場合）API接続仕様・画面遷移がコードと一致するか | コンポーネント仕様書「API接続仕様」「画面遷移」とfetch/axios呼び出し・Navigate/Routerの実装を照合 |
| （`frontend`の場合）Zodスキーマが入力バリデーション仕様と一致するか | コンポーネント仕様書「入力バリデーション（Zodスキーマ）」とZodスキーマ定義を照合 |
| 用語・変数名・メッセージ文言等の表記が設計書と一致するか（CPC-2） | 詳細設計WB・プログラム仕様書の用語とコード内の識別子・コメントを照合 |

#### チェック B: 製造コード → テストコードの整合性

| 確認項目 | 確認方法 |
|---|---|
| Serviceテストのモック設定がRepositoryの実シグネチャと一致するか | ServiceImplテストの `when(repository.xxx)` と RepositoryImpl を照合 |
| Controllerテストのモック設定がServiceの実シグネチャと一致するか | ControllerテストのMock設定とServiceImpl を照合 |
| テストされていないパブリックメソッドがないか | 各実装クラスとテストメソッドの一覧を照合 |
| （`frontend`の場合）MSWのモック設定が実際のAPIレスポンス型と一致するか | `TEST_HANDLERS`のレスポンス型とコンポーネント/フックの型定義を照合 |
| （`frontend`の場合）テストされていない公開コンポーネント/フックがないか | 対象ディレクトリの`.tsx`/`.ts`一覧とテストファイル一覧を照合 |

#### チェック C: テストシナリオ.md → テストコードの整合性

| 確認項目 | 確認方法 |
|---|---|
| 受け入れ条件カバレッジ表の全テストケースが存在するか | テストシナリオ.mdのカバレッジ表と実テストメソッドを照合 |
| 正常系・異常系・境界値テストが全件実装されているか | テストシナリオ.mdの各観点と照合 |
| 認証・認可テスト（AUTH-N）が実装されているか | テストシナリオ.mdの認証テストとControllerテストを照合 |
| （`frontend`の場合）コンポーネントテスト観点（表示要素/Props・State/ユーザ操作）が全件実装されているか | テストシナリオ.mdの「コンポーネントテスト観点」と実テストを照合 |

#### チェック D: 詳細設計書 → テストコードの整合性（値の正確性）

チェックA（設計⇔コード）・チェックB（コード⇔テストの構造整合性）はいずれも「テストのアサーション**値**が設計書の値と一致しているか」を見ていない。この盲点を直接照合するのがチェックDの役割（A/B/Cとは直交する軸）。

| 確認項目 | 確認方法 |
|---|---|
| 境界値の入力・期待結果が設計書の具体的数値と一致するか | service.md「業務ルール」の数値とテストのパラメータ・アサーションを照合 |
| バリデーションエラーのエラーコード/メッセージCDがテストと一致するか | controller.md／プログラム仕様書のメッセージCD列とテストの`assertThrows`/`verify`を照合 |
| 例外メッセージ本文がメッセージ一覧.mdと一致するか | メッセージ一覧.mdの本文とアサート文字列を照合 |
| 外部IF連携のエラーコードがモックレスポンスと一致するか（該当時） | 外部IF定義書のerrorCdとテストのモック設定を照合 |
| （`frontend`の場合）表示文言・エラーメッセージが設計書の記載と一致するか | コンポーネント仕様書の文言とテストのアサーション文字列（`getByText`等）を照合 |
| （`frontend`の場合）Zodバリデーションのエラーメッセージがテストと一致するか | 「入力バリデーション」表のエラーメッセージ列とテストのアサーションを照合 |
| アサーション文字列・変数名の用語が詳細設計・メッセージ一覧と一致するか（CPC-2） | メッセージ一覧.mdの表記とテストのアサーション文字列を照合 |

### Step 4: 手戻りワークフローの起動（統一フロー）

不整合を発見した場合は **全て手戻りワークフローを経由する**。「通常手戻り（閉じた修正）」と「rework（横断機構）」の2分岐は廃止し、単一フローで処理する。ルールを一本化することで人間・AI 双方の判断ブレを防ぐ。

手順（インラインフィックス判定〜大規模手戻りエスカレーション）は `.claude/rules/cross-process-consistency.md`「不整合発見時の手戻り連携手順」（手順1〜手順5）を正典として適用する。本スキル固有の補足のみ以下に残す。

#### PT工程固有の補足（手順2: 既存チェックとの重複確認）

設計書自体に誤りがある場合、チェックA（コードとの不一致）とチェックD（テストとの不一致）が同一の根本原因から個別に検出されうる。手戻りID採番の前に、今回の不整合が指す原因箇所（設計書の同一セクション）が、チェックA/B/Cで既に別の不整合として記録されていないか確認する。同一原因の場合は手戻りIDを1つに統合し、レポート内で相互参照する（「関連: チェックA-{n}と同一原因」）。自動マッチングは行わず、人間・AIによる目視確認で十分とする。

#### PT工程固有の補足（手順3: rework-impact-report.md の格納先）

`consistency-check` は PT 工程内のためスタックリポ側で実施され、rework-impact-report.md の格納先は通常 `{スタック}/specs/{案件キー}/rework/{手戻りID}/`（原因工程が SS/PG/PT の場合）になる。

## 制約

- ✅ 不整合箇所はファイル名・メソッド名・行番号を具体的に示す
- 🚫 「問題なし」と断言せず、確認した項目を必ず明示する
- ✅ テストが存在しないパブリックメソッドは必ず指摘する
