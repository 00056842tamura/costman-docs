# 基本設計成果物（docs/base-design/）

> 工程2 UI（基本設計）の永続成果物を格納する（プロダクトルート・案件横断で集約）。
> 直接編集モデル: UI 工程はここへ直接書き込む。検討メモ（discussion-log・adr）は `specs/{案件キー}/base-design/{issue_id}/`。**実装対象クラス一覧・テストシナリオ・テーブル一覧・テーブル定義書は specs に退避せず、本ディレクトリの正式成果物として直接生成する。**

## ファイル構成

|---|---|---|

| `Web_API_IF一覧表.md` | 案件横断・単一 | 全機能の API 一覧。`issue-to-design` が自動追記 |
| `Web_API_IF定義書_{機能ID}.md` | per-機能（**1機能ID=1API**） | API 仕様 |
| `シーケンス図_{機能ID}.md` | per-機能 | 機能単位のシーケンス図 |
| `機能概要_{機能ID}.md` | per-機能 | 機能単位の概要 |
| `テーブル一覧.md` | 案件横断・単一（累積） | **テーブルID（T###）採番の正本**。テーブル名・概要・参照する機能ID一覧（参考）を記録。`basic-design-gen` が追記（**bs / batch のみ**） |
| `テーブル定義書_{テーブルID}_{テーブル名（論理）}.md` | per-テーブル（**1テーブル=1ファイル。bs / batch のみ**） | DB テーブル定義（カラム定義・インデックス・外部キー制約）。**正本はここ。工程4 SS は読み込み専用**（実装時の変更は手戻りでUI issueへ戻す）。要件ID・機能ID単位のファイルではない（テーブルは複数の要件ID・機能IDから参照されうる） |

## 命名・採番
- 要件ID（`R001`・SA 採番・`docs/requirements/要件一覧.md` が正本）を UI 工程でスタック×API/画面/ジョブ単位に分解し、機能ID（`{カテゴリ}-{3桁連番}`。カテゴリは `bs`/`batch`/`us-intra`/`us-inter`/`front-intra`/`front-inter` の6種でそれぞれ独立した3桁ゼロ埋め連番。**正本は `docs/base-design/機能一覧.md`**）を採番する（**1機能ID=1API/1画面/1ジョブ**）
- 既存の API ID・ジョブID は廃止せず、機能一覧.md の「既存ID」列で機能IDとの対応を管理する
- テーブルID（`T001`・3桁ゼロ埋め・単一連番。**正本は `docs/base-design/テーブル一覧.md`**）は機能IDとは独立に採番する（**1テーブル=1テーブルID**）。テーブルは複数の要件ID・機能IDから参照されうるため、要件ID・機能ID単位では採番しない
- per-機能ファイルは `{種別}_{機能ID}.md`。UI issue単位・案件横断で累積するファイル（実装対象クラス一覧.md・テストシナリオ.md・クラス図.md・テーブル一覧.md）は `_{機能ID}` サフィックスなし。**例外**: テーブル定義書は per-機能ではなく per-テーブルで、`{種別}_{テーブルID}_{テーブル名（論理）}.md`（要件ID・機能IDは使わない）

## 生成元・運用
- PSK40 テンプレ（`docs/templates/40_基本設計/`）を `basic-design-gen` が `_{機能ID}` 命名でコピー・記入する（機能一覧.md・Web_API_IF一覧表.md・実装対象クラス一覧.md・テストシナリオ.md・クラス図.md・テーブル一覧.md は無サフィックスのまま追記。テーブル定義書のみ `_{テーブルID}_{テーブル名（論理）}` 命名）
- `機能一覧.md`・`Web_API_IF一覧表.md` は案件開始（`/case-init`）で初期化し、UI 工程で機能行を追記する
- Web_API_IF定義書・実装対象クラス一覧・テストシナリオ・クラス図は**プロダクトレベル**（複数スタックが参照）。テーブル一覧・テーブル定義書は bs/batch のみで、UI工程が正本（SS工程は読み込みのみ）。テーブル定義書はテーブル単位で管理し、要件ID・機能ID単位ではない

## ⚠️ 並行案件時の注意

### `Web_API_IF一覧表.md`・`テーブル一覧.md` の同時追記コンフリクト

`Web_API_IF一覧表.md`・`テーブル一覧.md` はいずれもプロダクト横断の単一ファイルです。2案件が同時に UI 工程を進めてこれらのファイルへ行を追記すると、`feature/{案件キー}` へのマージ時にコンフリクトが発生します。

**対処:**
- UI 工程は1案件ずつ完了させてから次案件の UI を開始する（推奨）
- 並行が避けられない場合はコンフリクト発生を想定してマージ時に両方の追記行を保持する

### per-機能ファイル（`_{機能ID}.md`）・per-テーブルファイル（`_{テーブルID}_{テーブル名}.md`）は衝突しない

機能ID（`{カテゴリ}-{3桁連番}`）はカテゴリごとに独立しているが、各カテゴリ内はプロダクト横断の単一連番のため、異なる案件のファイルは（同カテゴリ内では）別番号になり衝突しません。テーブルID（`T###`）もプロダクト横断の単一連番のため同様に衝突しません（`機能一覧.md`・`テーブル一覧.md` への同時追記コンフリクトのリスクと対処は `.claude/rules/github-ops.md` の「並行案件（同時進行）時の運用ガイドライン」を参照。要件ID（R###）採番の競合については `docs/requirements/README.md` を参照）。
