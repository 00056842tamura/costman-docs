# ADR-007: `check_typescript.py` の `any` 型検知が実質的に機能しない正規表現欠陥の解消

> ✅ **本ADRは実装済み**（2026-07-08）。ADR-006（既存Write/Editフックのブロック実効性欠陥）の実装検証中に発見した、別系統の欠陥。

## 目的（この対応で達成したいこと）

- **Why（なぜ対応するか）**: `.claude/hooks/check_typescript.py`は`.claude/rules/reacter-coding-standards.md`が定める「`any`型使用禁止（`@typescript-eslint/no-explicit-any`はWARN設定だが、`.claude/hooks/`のPreToolUseフックとしては禁止として実装されている）」を検知する目的で正規表現チェックを持つが、実際のTypeScriptコードで最も一般的な書き方では検知できないことが判明した。ADR-006でstdin/exit code周りの欠陥を解消し「フックは実際にブロックする」ようになった今、この個別チェックの正規表現自体が機能しないままでは、`any`型禁止という規約が実効性を持たない。
- **What（何を対応するか）**: `check_typescript.py`の`any`型検知正規表現の否定後読み `(?<!\w)` を除去し、`変数名: any`という最も一般的な書き方を含め正しく検知できるようにする。
- **How（どう対応するか）**: 正規表現を`(?<!\w)(:\s*any\b|as\s+any\b|<any>|Array<any>)`から、コロン直前の文字種を問わない形に変更する。既存のテストケース（`console.log`等・他の禁止パターン）への影響がないことを確認する。

## 背景

### ①状況

ADR-006の対応計画を実装した後、`check_typescript.sh`（新設ラッパー）を経由して`any`型違反のテストケース（`const x: any = 1;`）を投入したところ、検知されず`exit 0`（違反なしと判定）で通過した。他の禁止パターン（`console.log`）は同じ経路で正しく`exit 2`（ブロック）になることを確認済みだったため、ADR-006で修正した入力取得・exit code・stdin処理自体は正しく機能しており、`any`型検知固有の問題であると判断した。

### ②課題・問題

対象の正規表現は以下の通り。

```python
re.search(r"(?<!\w)(:\s*any\b|as\s+any\b|<any>|Array<any>)", stripped)
```

`(?<!\w)`は「マッチ開始位置の直前の文字が単語文字（`[a-zA-Z0-9_]`）でないこと」を要求する否定後読みである。しかし、TypeScriptの型注釈`変数名: any`では、コロンの直前は常に識別子の末尾（単語文字）になる。つまり`:\s*any\b`にマッチしようとする位置（コロンの直前）の直前の文字は、識別子の実質的に全てのケースで単語文字であり、否定後読みが常に不成立になる。

実際に検証した結果は以下の通り。

```python
>>> import re
>>> pattern = r"(?<!\w)(:\s*any\b|as\s+any\b|<any>|Array<any>)"
>>> re.search(pattern, "const x: any = 1;")
None                          # 検知されない（実際のコードで最も一般的な書き方）
>>> re.search(pattern, "function f(x: any) {}")
None                          # 検知されない
>>> re.search(pattern, "const z:any=1;")
None                          # 検知されない
>>> re.search(pattern, "let y : any;")
<re.Match object; span=(5, 12), match=' : any'>   # 検知される（コロンの前に空白を1つ挟む書き方）
```

`as any`・`<any>`・`Array<any>`の3パターンも同じ否定後読みの影響を受けるが、これらは`as\s+any`（`as`という単語文字の直後にスペースが必ず入る）・`<any>`（`<`は単語文字でない）という形であり、`:\s*any`と異なり否定後読みが不成立にならないケースが多い（`as any`の場合、`as`の直後の空白がマッチ開始位置の直前になるため単語文字ではなく、否定後読みは成立する）。実質的に問題があるのは`:\s*any\b`パターンのみである。

なお、`(?<!\w)`という否定後読みが当初何を意図していたかは特定できなかった（コミット履行時の意図が記録されていない）。推測としては「`fooany`のような識別子の一部を誤検知しない」ことを狙ったものと考えられるが、`\bany\b`の`\b`（単語境界）で既に同じ効果が得られるため、`(?<!\w)`は`:\s*any\b`パターンに対しては不要かつ有害である。

### ③制約

- 他3パターン（`as any`・`<any>`・`Array<any>`）の検知動作を変えない。
- 他の禁止パターン（`React.FC`・`dangerouslySetInnerHTML`・`innerHTML`・`window.alert`・`console.log`・`debugger`・TODO・package.jsonバージョンワイルドカード）は本ADRの対象外（影響なし）。
- ADR-006で修正済みの入力取得・exit code・ラッパースクリプトの仕組み自体は変更しない。

## 決定事項

`check_typescript.py`の`check_typescript()`関数内、`any`型検知の正規表現を以下に変更する。

```python
re.search(r"(:\s*any\b|(?<!\w)as\s+any\b|<any>|Array<any>)", stripped)
```

`:\s*any\b`パターンからのみ`(?<!\w)`を除去し、`as\s+any\b`パターンには維持する（`as`単体は単語文字の並びであり、他の識別子の一部（例: `alias`の一部に見える誤検知）を避けるため、この部分は元の意図を保持する）。`<any>`・`Array<any>`は`<`が単語文字でないため元々否定後読みの影響を受けておらず変更不要（ただし可読性のため同じ括弧グループ内にそのまま残す）。

## 理由

- `:\s*any\b`のみ否定後読みを外すのは、この1パターンのみが実際に誤って機能不全を起こしているためである（②の実証結果参照）。`as\s+any`・`<any>`・`Array<any>`は現状のままで意図通り機能しており、変更する理由がない。
- `\b`（単語境界）が既に「識別子の一部への誤マッチ防止」の役割を果たしているため、`:\s*any\b`から`(?<!\w)`を除去しても新たな誤検知（false positive）は生じない。`:`という文字自体が単語文字ではないため、`fooany: any`のような識別子直後にコロンが来るケースでも、マッチ対象は`: any`の部分のみであり誤りは生じない。

## 影響

- `check_typescript.py`（`.claude/hooks/`）の1箇所のみを変更する。
- 修正後、`変数名: any`という最も一般的な書き方を含む`any`型使用が、Write/Editツール実行時に正しくブロックされるようになる（これまで実質的に検知されていなかった規約違反が、初めて実効化される）。
- `check_typescript.sh`（ADR-006で新設したラッパー）・`.claude/settings.json`の設定・他の禁止パターンは変更しない。

## 未確定事項（バックログ）

- [ ] `(?<!\w)`という否定後読みが当初どのような意図で追加されたかは特定できなかった。将来的に別の意図（例: コメント内の`: any`を除外する等）があった可能性は否定できないが、`check_typescript()`内では既に行頭からコメント判定（`is_comment`）を別途行っているため、この用途である可能性は低いと判断した。
