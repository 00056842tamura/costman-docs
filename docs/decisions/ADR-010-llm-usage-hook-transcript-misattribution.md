# ADR-010: 工数計上フック（Stop/SubagentStop）の記録欠落・過小集計の根本原因と対応

> ✅ **本ADRは実装済み**（2026-07-15）。別プロダクトの実運用調査結果（原因1・原因2の2仮説）を引き継ぎ、本リポジトリで実機診断・再現実験を行った結果、**当初の2仮説とは異なる、決定論的な2つのロジックバグ**が根本原因であることを特定し、修正・実機再現テストまで完了した。

## 目的（この対応で達成したいこと）

- **Why（なぜ対応するか）**: 別プロダクトの実運用で、`.claude/hooks/log_llm_usage.py`（Stop/SubagentStop フック・`llm-usage.jsonl` への工数記録）が高頻度に記録漏れを起こす事象が確認された（SS工程12 issue中、記録が残ったのは1 issueのみ・かつ1行だけ）。この記録は `/usage-report` の集計対象であり、記録漏れは案件のLLM工数実績を不正確にする。
- **What（何を対応するか）**: 引き継ぎ時点の仮説は「原因1: スコープ解決（ブランチ名解析・編集ファイル推論）の脆弱性」「原因2: バックグラウンドAgent並行完了時の競合」の2つだったが、実機診断ログによる再現実験で、**実際の根本原因は仮説と異なる、以下2つの決定論的バグ**であることが判明した。
  1. `SubagentStop` の hook 入力の `transcript_path` は常に**親（メイン会話）セッション**のトランスクリプトを指し、サブエージェント自身の実行内容を一切含まない（`agent_transcript_path` という別フィールドが正しいトランスクリプトを指すが、コードはこれを読んでいなかった）。
  2. トランスクリプト中の「直前のユーザー発言」境界判定が、ツール実行ループの折り返し（`tool_result` を運ぶ合成 `user` エントリ）を新規ユーザー発言と区別できず、境界が直近のツール往復まで前進し、それより前のツール呼び出しターン（usage・編集ファイルパスとも）が集計から漏れる。加えて、1ターンがストリーミングで複数トランスクリプトエントリに分割される場合、同一ターンの usage を重複加算していた。
- **How（どう対応するか）**: `.claude/hooks/log_llm_usage.py` の `transcript_path` 選択・境界判定・usage集計ロジックを修正し、実機再現実験（単発3回・4並行×3ラウンド＝12件）で修正後の動作を確認した。加えて、引き継ぎ計画の「原因1」対応として計画されていた `issue-init` 側のスコープ確定マーカー（`.claude/.issue-scope.json`）も実装し、ブランチ名解析・編集ファイル推論への依存を追加で下げた。引き継ぎ計画の「原因2（並行完了時のフォールバック記録）」は、再現実験で一度も再現しなかったため実装しないと判断した。

## 背景

### ①状況

別プロダクトの実運用（SS工程・複数機能IDをバックグラウンドAgentで並行実施）で、`llm-usage.jsonl` への工数記録が高頻度に欠落する事象が発覚した。引き継ぎ時点の実測:

- 単発（並行数1）で完了したケース（bs-004）: 正しく記録されていた。
- 4件同時起動したケース（bsスタック×4）: 1件だけ記録が残り、残り3件は0件。
- 4件同時起動した別のケース（us-apiスタック×4）: 全4件が0件。
- 2件同時起動したケース（frontendスタック×2）: `<task-notification>` では両エージェントとも多数のツール呼出・大量のトークンを使ったことが確認できたにも関わらず、両方とも0件。

引き継ぎ時点の仮説は以下の2つだった。

- **原因1（部分対応済みとされていた）**: `log_llm_usage.py` が発火するたびに「その応答で編集された全ファイル」から所有リポジトリ・ブランチを都度再導出しており、1応答内でissueに属さない付帯編集が混ざると誤解決・記録漏れが起きる。
- **原因2（未確定・要検証）**: バックグラウンドで並行完了するサブエージェントの記録が、ハーネス側の競合により消える。

### ②課題・問題（実機診断で判明した実際の根本原因）

本リポジトリで、一時的な診断ログ機構（`.claude/.hook-debug-enabled` マーカーでオプトイン。本番の `llm-usage.jsonl` とは別ファイル `.claude/hook-debug.log` に出力。既定は無効）を `log_llm_usage.py` に追加し、隔離環境（ネストした独立git リポジトリ＋機能ID別の `git worktree` で実際のスタックリポ運用を模倣）で `Agent` ツールを実際に起動して実証した結果、引き継ぎ時点の2仮説とは異なる、以下2つの決定論的バグが判明した。

**発見1: `transcript_path` は常に親セッションのトランスクリプトを指す**

`log_llm_usage.py` は `data.get("transcript_path")` を読んでいたが、これは **`SubagentStop` イベントでも常に呼び出し元（メイン会話）セッション自身のトランスクリプトパス**であり、当該サブエージェントの実行内容（`tool_use`・応答テキスト等）を一切含まない。実際のhook入力（診断ログで実測）を以下に示す。

```json
{
  "session_id": "053001c4-...",
  "transcript_path": "...\\053001c4-....jsonl",              // ← 親セッション自身のトランスクリプト
  "agent_id": "a39343f1ddc3fbc09",
  "hook_event_name": "SubagentStop",
  "agent_transcript_path": "...\\053001c4-...\\subagents\\agent-a39343f1ddc3fbc09.jsonl"  // ← 当該サブエージェント自身のトランスクリプト（正しい値だが未使用）
}
```

修正前のコードは `transcript_path`（親セッション）を読み、「直前のユーザー発言以降のアシスタント応答」を集計・編集ファイル推定していた。親セッション（メイン会話）側の「直前のユーザー発言」は、通常メイン会話自身の直近のツール往復であり、当該サブエージェントが何をしたかとは無関係。このため:
- メイン会話が直近で編集した無関係なファイルから誤ったブランチ・issueに帰属してしまう（≒原因1の症状と類似するが、原因は「推論の脆弱性」ではなく「そもそも見るべきトランスクリプトが違う」）。
- メイン会話の直近ツール呼出にファイルパスを持つものが無ければ `edited_path=None` となり、常に解決不能で記録されない。
- **複数のサブエージェントが同時に完了すると、それら全ての `SubagentStop` イベントが「同一の」親セッショントランスクリプトを見るため、全て同一の（誤った）branch/edited_pathに収束する。** 4機能IDを並行起動した場合、「たまたま親セッションの直近編集ファイルが解決できる状態だった1件のみ記録が残り、残り3件は同一ファイルへの重複書き込みか0件になる」「親セッションの直近状態が解決不能なら全件0件になる」という、引き継ぎ時点で実測された症状（「1件だけ残り3件0件」「4件全て0件」）と正確に一致する。

**発見2: `tool_result` エコーが「新規ユーザー発言」と誤判定される（境界前進バグ）＋ 同一ターンのusage二重集計**

トランスクリプト上は「人間の新規入力」も「直前の `tool_use` に対する `tool_result`」も同じ `type: "user"` として記録される。修正前の `entry_type(e)=="user"` 判定はこれらを区別しないため、「直前のユーザー発言」の境界が、同一やり取り内の直近のツール往復（`tool_result`）まで前進してしまう。

サブエージェント自身のトランスクリプト（`agent_transcript_path` を正しく使った場合）を実際に読んだ結果、以下の構造だった（Write 1回・応答1回の単純なタスク）。

```
0 user      (実タスクプロンプト)
1-2 attachment
3 assistant (thinking)              message.id=msg_...RsJPF...  usage含む
4 assistant (tool_use: Write)       message.id=msg_...RsJPF...（entry3と同一・streaming分割）
5 user      (tool_result)           ← 修正前コードはここを「直前のユーザー発言」と誤判定
6 assistant (thinking)              message.id=msg_...zVFm...
7 assistant (text: "done")          message.id=msg_...zVFm...（entry6と同一・streaming分割）
```

修正前は境界が entry5（`tool_result`）になり、集計対象が entry6-7 のみに限定される。結果:
- entry3-4（実際にファイルを書いたターン）の usage・編集ファイルパスが完全に集計から漏れる。`edited_path` は常に `None` になり、発見1を修正しただけでは branch/work_logs の解決に失敗し続ける（発見1と発見2は独立ではなく、両方の修正が揃わないと機能しない）。
- さらに、entry6とentry7は**同一ターン（同一 `message.id`）がストリーミングにより2エントリに分割**されたものであり、`message.usage` は両エントリで完全に同一の値を持つ（実測: `input_tokens=8, output_tokens=43, cache_read_input_tokens=88695, cache_creation_input_tokens=3959` が entry6・entry7 両方に出現）。修正前のコードは `assistants` 全件を無条件に加算していたため、**集計対象に含まれたターンの usage を2倍に過大集計**していた（entry3-4 も同様に同一 `message.id` で重複）。

### ③制約

- 引き継ぎ時点の「原因2（並行完了時の競合）」について、発見1・発見2を修正した状態で実機再現実験（`Agent` ツールを実際に起動。単発を1回・3並行×3ラウンド以上ではなく実際は「単発1回＋4並行×3ラウンド＝12件」）を行った結果、**12件すべてで欠落・例外が0件**だった（診断ログの `input`/`transcript`/`scope`/`written` 各ステージが毎回4件ずつ・整合して記録された）。したがって、**「ハーネス側の並行実行時の競合」という意味での原因2は、本検証の範囲では再現しなかった**。引き継ぎ時点で観測された症状は、発見1・発見2の2バグで説明可能であり、これらを修正した上で追加のフォールバック機構（Step4）を実装する必要はないと判断した。
- 本ADRの修正・検証は Windows・Git Bash・Claude Code CLI（`claude-sonnet-5`／サブエージェントは `claude-haiku-4-5`）環境で実施した。他プラットフォーム・他バージョンでの `agent_transcript_path` フィールドの存在・安定性は未確認（Claude Code の非公開実装詳細に依存するため、将来のバージョンで変更される可能性がある。フォールバックとして `transcript_path` を保持しているため、フィールドが削除された場合も即時に全損することはない）。
- 隔離環境は本リポジトリ直下の一時ディレクトリ（`specs/hooktest-2026-001/`）とOS一時フォルダ配下のネストしたgitリポジトリ・worktreeで構成し、検証後にすべて削除済み。実装差分には検証用ファイルは含まれない。

## 決定事項

1. `log_llm_usage.py`: `transcript_path` の選択を `data.get("agent_transcript_path") or data.get("transcript_path") or ...` に変更する（`SubagentStop` では常に前者が使われ、`Stop`〔`agent_transcript_path` が無い〕では後者にフォールバックする）。
2. `log_llm_usage.py`: 「直前のユーザー発言」境界判定を、`tool_result` のみで構成される合成 `user` エントリを除外した `find_last_real_user_index()` に統一する（`summarize_latest_exchange`・`find_latest_edited_path` の両方で使用）。
3. `log_llm_usage.py`: usage集計を `message.id` 単位でデデュープしてから合算する（同一ターンがストリーミングで複数エントリに分割される場合の二重集計を回避）。
4. `log_llm_usage.py`: 上記の判定過程を可視化する診断ログ機構（`.claude/.hook-debug-enabled` または環境変数 `CLAUDE_HOOK_DEBUG=1` でオプトイン。既定は無効・本番の `llm-usage.jsonl` とは別ファイル）を追加し、恒久的に残す（silent-failure設計のフックは将来も同種の不具合が再発しうるため、調査手段を常備する）。
5. `log_work.py`: `issue-init` が書き込むスコープ確定マーカー（`.claude/.issue-scope.json`。ローカル・未追跡ファイル）を最優先で読む `read_issue_scope_marker()` を追加し、`resolve_issue_work_logs()` の先頭で使用する（マーカー無し時は既存のブランチ名解析に完全フォールバック）。これは引き継ぎ計画の「原因1対応」に相当し、発見1・発見2とは独立に、ブランチ名解析・編集ファイル推論への依存を下げる防御的多重化として実施する。
6. `issue-init` の SKILL.md（SA/UI/SS-Plan/PG-Plan/PT-Plan の Step 3、SS/PG/PT の Step S2）に、ブランチ作成直後のマーカー書き込み手順を追記する。
7. 引き継ぎ計画の「Step4（並行完了時のフォールバック記録）」は実装しない（③制約参照）。

## 理由

- 発見1・発見2は実機診断ログと実際のトランスクリプト構造の直接観察により特定した、再現性のある決定論的バグであり、推測ではない。修正後の実機再現実験（単発・4並行×3ラウンド）でも欠落・例外0件を確認済みである。
- 引き継ぎ計画のStep3（スコープ確定マーカー）は、発見1・発見2の修正後も残る「ブランチ名解析・編集ファイル推論に依存する」という設計上の脆弱性（1応答内で複数スコープの編集が混在する場合の誤解決リスク）に対する独立した防御であり、根本原因の特定後も実施する価値があると判断した。既存ロジックへの完全フォールバックを保つことで、後方互換性（既存ブランチ・移行期間中の挙動）を壊さない。
- 引き継ぎ計画のStep4は、根本原因が「ハーネス側の並行実行競合」ではなく「常に同一の誤ったトランスクリプトを読む決定論的バグ」であったことが判明し、そのバグ自体を修正した時点で追加のフォールバック機構が不要になったため、実装しないことにした（再現実験で経験的に裏付けた上での判断）。
- 診断ログ機構は「一時的な調査用」で終わらせず恒久機能として残すことにした。理由: 本フック群は元来 silent-failure 設計（記録の成否がユーザーからは見えない）であり、今回のような記録漏れは通常の使用では発覚しにくく、発覚しても原因特定に長時間を要する。オプトイン（既定無効・ゼロオーバーヘッド）の恒久的な調査手段を残すコストは小さく、再発時の原因特定コストを大きく下げる。

## 影響

- `log_llm_usage.py`・`log_work.py` の修正により、**これまで実質的に機能していなかった `source: "subagent"` の工数記録が、単発・並行完了とも正しく記録されるようになる**。これは既存の集計（`/usage-report`）に、これまで欠落していた分の記録が新たに加わることを意味する（過去に記録されなかった分を遡及的に補完するものではない。修正後の新規実行分から正しく記録される）。
- 過去に記録済みの `llm-usage.jsonl` の内容（欠落していない分）については、修正前のロジック起因で**過小集計されていた可能性がある**（発見2のターン境界バグ・二重集計バグにより、実際の使用量と異なる値が記録されていた可能性）。既存の記録を遡及的に補正する対応は本ADRのスコープ外（対象案件のログ再集計が必要な場合は別途判断）。
- `issue-init` にスコープマーカー書き込み手順が追加されることで、SA/UI/SS-Plan/PG-Plan/PT-Plan・SS/PG/PT の全工程着手フローに1手順が増える（自動化された `mkdir`+`cat > ... <<EOF` のみで人間の追加判断は不要）。
- マーカーファイル（`.claude/.issue-scope.json`）はローカル・未追跡（本リポジトリ・案件リポは `.gitignore` 済み）である。**スタックリポ側の `.gitignore` は標準チーム受領テンプレート由来であり本リポジトリの管理外**のため、各スタックリポで個別に除外設定を確認・追記する必要がある（SKILL.md にその旨のガイドを記載した）。追記を怠った場合、マーカーがコミットされ、後続の別ブランチへのマージ時に古いスコープ情報が残留するリスクがある（フォールバック〔ブランチ名解析〕が効くため記録が完全に誤帰属することはないが、意図しないスコープでの記録が発生しうる）。
- 診断ログ（`.claude/hook-debug.log`）・マーカー無効化フラグ（`.claude/.hook-debug-enabled`）はいずれもローカル・未追跡（`.gitignore` 済み）で、既定は完全に無効（既存の本番動作に影響なし）。

## 実装（差分概要）

- `.claude/hooks/log_llm_usage.py`:
  - `transcript_path` 選択に `agent_transcript_path` 優先を追加。
  - `entry_type()` はそのまま維持し、新規 `is_synthetic_user_turn()`・`find_last_real_user_index()` を追加して `summarize_latest_exchange()`・`find_latest_edited_path()` の境界判定を統一。
  - `summarize_latest_exchange()` の usage 集計を `message.id` 単位のデデュープ後に合算する方式へ変更。
  - `is_debug_enabled()`・`debug_log()` を追加し、主要な分岐点（input/transcript/scope/written/abort/exception）に診断ログ呼び出しを追加。
- `.claude/hooks/log_work.py`:
  - `read_issue_scope_marker()` を追加。
