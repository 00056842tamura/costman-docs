# frontend実装の正規フロー再生成 計画

- 作成日: 2026-08-24
- 案件キー: costman-2026-001
- 作成者: Claude Code（Sonnet 5）
- 位置づけ: `specs/costman-2026-001/meta.md`・`frontend/specs/costman-2026-001/rework/` への正式記録前の作業計画メモ

## 背景・目的

`frontend/src/features/` の現行実装（front-intra-001〜007、7画面）は、`costman-frontend` リポの PR #2「frontend実装の同期」を通じて投入されたものであり、以下の統制上のギャップを抱えている（詳細は `生成レポート/frontend設計書駆動再生成_作業状況レポート_20260821.md` に記録済み、および本セッションでの調査結果）。

- `frontend/specs/costman-2026-001/detail-design/{issue_id}_{機能ID}/` 配下の **WB（`frontend.md`）・`ADR-SS-*.md`・`review-report.md`** が front-intra-001〜007 のいずれも未整備
- PR のベースブランチが `develop` であり、`feature/costman-2026-001` 統合ブランチを経由していない
- 正規のSS工程スキル（`/detailed-design-gen` → `/detailed-design-review-frontend`）・PG工程スキル（`/reacter-code-gen` → `/reacter-code-review`）を経由せず生成されたため、生成物が「本当に `docs/base-design/` の基本設計書のみを正しく踏襲しているか」の検証記録が存在しない
- 既知の軽微不整合: front-intra-001 のコンポーネント名（仕様書は `TopPage`、実装は `Top.tsx`）

ユーザーの意向は「今のコードをそのまま記録だけ後追いする」のではなく、**正規フローが本来参照すべき資材（`docs/base-design/` の基本設計書 → SS工程で正式に確定させた詳細設計書）から、7画面すべてを再生成し直す**こと。

## 現状と目標状態の相違点（機能ID共通で発生している構造的ギャップ）

| 観点 | 現状 | 目標（正規フロー） |
|---|---|---|
| SS工程の実施記録 | なし（`/detailed-design-gen`未実行） | issue起票→`/detailed-design-gen`実行→`ADR-SS-{n}.md`起票 |
| SS工程のレビュー | なし | `/detailed-design-review-frontend` 実行→`review-report.md` |
| SS成果物のWB | 未整備 | `frontend.md`（機能ID単位）を正式生成 |
| PG工程の実施記録 | issue未起票（PR#2はissue外で生成） | `/issue-init 工程: PG`→ブランチ作成 |
| PG工程のコード生成 | 出自不明（`new_docs`経由 or 別セッション生成、系譜が交錯） | `/reacter-code-gen` で確定済みSS成果物から生成 |
| PG工程のレビュー | なし | `/reacter-code-review`→`reacter-code-review-report.md` |
| 統合ブランチ経由 | `develop`直マージ | `feature/costman-2026-001-pg-{機能ID}`→統合ブランチ経由PR |
| 手戻り管理 | 未記録 | `specs/costman-2026-001/meta.md` 手戻り管理表に `sp-{3桁}` を採番して記録（本体PRが `develop` へマージ済みのため、`cross-process-consistency.md`「本体PRマージ後に発覚した場合の手戻り判定」に従い手戻り相当として扱う） |

対象は front-intra-001〜007 の7画面すべて。

## 作業方針（案件横断の共通ステップをまず確定し、機能ID単位で繰り返す）

### Step 0: 手戻りIDの採番とスコープ確定
1. `specs/costman-2026-001/meta.md`（案件リポ）の手戻り管理表に `sp-{3桁連番}` を新規採番
2. 影響工程＝SS・PG（実施工程・frontendスタック内で影響が閉じる）→ 既存のSS sub-issue（#4〜#10、front-intra-001〜007）を Reopen する方針とする
3. `frontend/specs/costman-2026-001/rework/{手戻りID}/rework-impact-report.md` を作成（原因＝正規工程未経由での生成、影響範囲＝7機能ID全て、対応方針＝本計画）

### Step 1: SS工程のやり直し（機能ID単位・front-intra-001〜007）
各機能IDについて:
1. 対応するSS issue（#4〜#10）を Reopen、ブランチ `feature/costman-2026-001-ss-{機能ID}-sp-{手戻りID}` を作成
2. `docs/base-design/` の該当ドキュメント（機能概要・実装対象クラス一覧・テストシナリオ・画面状態遷移図・シーケンス図・非機能共通設計）を正本として読み込む
3. `/detailed-design-gen` を実行し、コンポーネント仕様書・画面アクション遷移図・共通設計書（スタック単位は1回のみ）・WB（`frontend.md`）を正規に生成
   - 既存の `frontend/docs/detail-design/` の内容は参考情報として扱ってよいが、正本は本ステップで新たに確定させたものとする
   - front-intra-001 の命名不整合（`TopPage`/`Top.tsx`）はこの過程で解消する（コンポーネント仕様書とコードの一致を取る）
4. `/detailed-design-review-frontend` を実行し `review-report.md` を生成、指摘があれば解消
5. `ADR-SS-{n}.md` を決定事項ごとに起票（特に既存実装からの変更点がある場合は理由を明記）
6. `docs-to-pr` でSS工程PR（ベース=`feature/costman-2026-001`）を作成

### Step 2: PG工程のやり直し（機能ID単位）
各機能IDについて:
1. `/issue-init 工程: PG` でPG issueを起票、ブランチ `feature/costman-2026-001-pg-{機能ID}-sp-{手戻りID}` を作成
2. Step1で確定したSS成果物（コンポーネント仕様書・共通設計書・WB）とUI工程の実装対象クラス一覧を入力に `/reacter-code-gen` を実行
   - 既存実装（現行 `src/features/{feature}/`）で手戻り sp-001（`convertHiddenRow`・`useErrorHandling` のバリデーション分岐）等、既に解消済みの実装上の教訓がある場合は、再生成後も同じ問題が再発しないか確認する
3. `/reacter-code-review` を実行し `reacter-code-review-report.md` を生成、指摘があれば `/springer-review-fix` 相当の修正サイクルで解消
4. `docs-to-pr` でPG工程PR（ベース=`feature/costman-2026-001`）を作成

### Step 3: 全機能ID完了後の整合確認
1. 7機能ID全ての SS/PG PR がマージされたことを確認
2. `npm run build` / `npx eslint src` / `npx tsc --noEmit` が成功することを確認
3. `specs/costman-2026-001/meta.md`・`frontend/specs/costman-2026-001/rework/{手戻りID}/` の記録を更新し、手戻りをクローズ

## 参照すべき既存資材（正本）

- `docs/base-design/機能一覧.md`・`実装対象クラス一覧.md`・`テストシナリオ.md`・`画面状態遷移図_front-intra-*.md`・`シーケンス図_front-intra-*.md`・`非機能共通設計.md`
- 既存の `frontend/docs/detail-design/` は参考情報（正本ではない。Step1で置き換える）
- 既知の実装教訓: 手戻り sp-001（`convertHiddenRow`／`useErrorHandling`）、コスト利用率参照画面の3点差異（並び替えフォーム・登録日表示・型構造）— 再生成後にリグレッションしないよう確認事項に含める

## 検証方法

- 各機能IDのPG PR作成前に `npm run build`・`npx eslint src`・`npx tsc --noEmit` が成功すること
- `/reacter-code-review` のレポートで未解決指摘が0件であること
- `.claude/hooks/check_review_gate.py` がSS（`review-report.md`・ADR最低1件）・PG（`reacter-code-review-report.md`）の成果物存在を確認できること（このゲートを通れば `gh pr create` が可能）
- 7画面全てで `docs/base-design/テストシナリオ.md` の受け入れ条件を満たすこと（目視確認は別途PT工程で実施）
